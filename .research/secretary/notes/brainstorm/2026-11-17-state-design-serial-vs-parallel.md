## 0. 先に結論

1. **「シリアルか並列か」は、「state の再帰をどの軸に走らせるか」の選択。** 並列は時間の軸だけに走らせ、マスの数だけ系列を並べる。シリアルは空間の軸に走らせ、フレームをつなぐと時間にも続く。位置合わせ（state を対応に沿って運ぶ）が意味を持つのは、state がマスに結び付いているときだけ（1.）。
2. **場所ごとの決定（私の推奨）**（7.）
   - 64段・対象別（今の A-b の場所）：**並列を維持**。位置合わせの spec がそのまま使える唯一の形。
   - 128段・256段：**並列で持ち越す根拠が弱い**。state の 3/4 を占め、動きのずれが一番大きい段なのに、運んでいない。持ち越しをやめる方向で、まず推論だけの診断をする。
   - 画面全体（Memory Attention の前）：入れるなら**シリアル**。ただし前のフレームの情報はほぼ届かない見込みで、時間方向の役には立たない。本線にしない。
   - 物体の領域だけ（マスク内シリアル）：**「物体ごとの state」の案**であり、手法1・object pointer と同じ欄に入る。今は作らない。
3. **ユーザーの仮説は、前半は成り立ち、後半は言い直しが要る**（6.）
   - 「位置合わせをするなら並列」は成り立つ。ただし、位置合わせの設計が並列を前提に作られているので、ほぼ言い換え。並列が優れている証拠ではない。
   - 「シリアルにすると位置の情報がなくなる」は不正確。なくなるのは、**マスごとの記憶**と**縦の隣との近さ**。現在のマスの位置は、位置埋め込みで渡せる。
   - 逆向きの事実がある。**位置合わせをしないなら、並列はシリアルより悪い**（因果的な設定での唯一の直接比較。Long-Context State-Space Video World Models の Table 5）。今の V3 で state の寄与が0付近なのと同じ向き。
   - 比べるべきは「並列＋位置合わせ」対「シリアル（位置合わせなし）」。これは文献にも手元にもない。
4. **メモリ**（4.）：先生の「全マスを1つの state にすると載らない」は、重みの数で見ると正しい（約 4.4×10¹² 個、17.6 TB）。state 自体は、並列が一番大きい（1物体・3段で約1.68億個、約576 MiB）。シリアルは約1.4万個。学習の VRAM の実測は、V3 が約22 GB（checkpointing なし）・約9 GB（あり）、Mamba なしが約4 GB。
5. **今日の計測（CPU）**（3.）：学習済みの V3・A-b の時定数は、初期値からほぼ動いていない。state の半減期は中央値で約11ステップ。並列なら11フレーム、シリアルなら11マス。シリアルで64段の1フレーム（4,096マス）先に残るのは、最大でも 2%。
6. **先行例が見つからなかったもの**：Mamba の state を対応や flow で運ぶ研究、物体のマスクの内側だけをスキャンする Mamba。どちらも「ない」とは断定できない（検索は数回）。
7. **次の一手**：位置合わせの spec を優先する方針は変えない。state の持ち方は、推論だけの診断2つと、画面全体シリアルの対照1本を、別の spec 案としてまとめた（10.）。

## 1. 問いの整理：案の一覧

64段（64×64＝4,096マス、256ch）で、Mamba は V3 と同じ設定（内部 512ch、`d_state` 16、`d_conv` 4）とする。1系列あたりの state は 512×(16＋4)＝10,240 個。

| 案 | state の単位 | 1フレームの読み方 | 次のフレームへ渡すもの | 同じマスの前フレームまでの距離 |
|---|---|---|---|---|
| **並列**（今の V3、A-b） | マスごと | 全マスを同時に1歩 | マスごとの state | 1ステップ |
| **ブロック** | b×b のブロックごと | ブロックの中を順に読む | ブロックごとの state | b² ステップ（4×4 なら 16） |
| **全体シリアル**（10/18 の V4） | 画面で1本 | 4,096マスを順に読む | 1本の state | 4,096 ステップ |
| **フレーム内シリアル** | なし（毎フレーム作り直す） | 4,096マスを順に読む | なし。時間は並列と組む | ― |
| **マスク内シリアル** | 物体ごとに1本 | マスクの内側のマスだけを順に読む | 1本の state | マスクの面積ぶん（数十〜数百） |
| **窓** | なし | 過去 K フレームの特徴を、対応に沿って並べ直して読む | 過去 K フレームの特徴 | 1ステップ（軌跡に沿って並べるため） |

- ブロックは、Long-Context State-Space Video World Models の block-wise scan の形。ブロックの大きさ1が並列、画面全体が全体シリアルで、2つの間をつなぐ。
- 窓は、Memory as Dynamics（直近8フレームを毎時刻作り直す）と TS-Mamba（軌跡に沿ってトークンを集める）の形。
- 並列は、「時間方向のシリアルを、マスの数だけ並べたもの」とも言える。窓の案で軌跡ごとに時間方向へ読むと、並列と同じ形になる。二分法は、見かけほどはっきりしていない。

### 2.1 画像：シリアルは位置をどう扱っているか、スキャン順はどれだけ効くか

| 論文 | 確かめたこと | 状態 |
|---|---|---|
| [Vision Mamba (Vim)](https://arxiv.org/abs/2401.09417)（ICML 2024） | Mamba の課題を "unidirectional modeling and lack of positional awareness" とし、双方向スキャンと位置埋め込みで補う。双方向にすると ImageNet 73.2→73.9、ADE20K 32.3→35.9 mIoU（Table 4）。差は分類で小さく、セグメンテーションで大きい | 確認済み |
| [VMamba](https://arxiv.org/abs/2401.10166)（NeurIPS 2024） | 4方向の cross-scan。位置埋め込みは使わない。スキャンの違い（Table 10、ImageNet）：DWConv ありで 単方向 82.26／4方向 82.60、DWConv なしで 80.88／82.25。"DWConv plays a critical role in establishing 2D priors" | 確認済み |
| [LocalMamba](https://arxiv.org/abs/2403.09338) | "significantly increasing the distance between vertically adjacent tokens"。Vim-T のスキャンを局所窓に替えると 73.1→74.1 | 確認済み |
| [PlainMamba](https://arxiv.org/abs/2403.17695)（BMVC 2024） | 行の折り返しの不連続を問題にし、連続したスキャンと、前のトークンがどの方向にあるかを知らせる項を足す。位置埋め込みも使う | 確認済み |
| [Spatial-Mamba](https://arxiv.org/abs/2410.15091)（ICLR 2025） | "its distance to the top or bottom neighbor equals to the image width"。state を近傍で混ぜると、スキャン1方向でも他の手法に並ぶ | 確認済み |
| [ZigMa](https://arxiv.org/abs/2403.13802)（ECCV 2024） | 空間の連続性を壊すと悪化する。Hilbert は zigzag より悪い（FID 27.38 対 13.32、Table 7）。位置埋め込みを足すと、Vision Mamba は FID 21.33→16.38、連続スキャンの ZigMa は 14.27→13.32（Table 2） | 確認済み（画像生成） |
| [2DMamba](https://arxiv.org/abs/2412.00678)（CVPR 2025） | 1D の Mamba は位置埋め込みで良くなる。2D 版ではスキャン順の影響は小さい | 確認済み（病理画像） |
| [Rethinking Scanning Strategies…Remote Sensing](https://arxiv.org/abs/2405.08493) | "A simple, single scanning direction is deemed sufficient"（セグメンテーション） | アブストラクトのみ |
| [Demystify Mamba in Vision](https://arxiv.org/abs/2405.16605)（NeurIPS 2024） | 忘却ゲートが "local bias and positional information" を与える。位置符号化で代わりができる、と分析 | 確認済み |
| [MambaOut](https://arxiv.org/abs/2405.07992) | 分類では Mamba は要らない。検出・セグメンテーションでは Mamba 系に届かず、長い系列の視覚タスクでは見込みがある、とする | 確認済み |

読み取り：シリアルにしても、位置は位置埋め込みで渡すのが普通（Vim、PlainMamba）。失われやすいのは、縦の隣が画像の幅ぶん遠くなること。スキャン順の効き方は条件しだいで、局所の畳み込みがあれば小さい（VMamba 0.34 ポイント）、空間の連続性を壊すと大きい（ZigMa）。

読み取り

- 動画認識は、全トークンを1本に並べる双方向スキャンが主流。ただしクリップ単位で、オンラインでは使えない。
- **オンラインで state を持ち越す例は、両方ある。** マスごと：AUSM、イベントカメラの SSM、TV3S。1本：FlashDepth、MambaLCT。
- **マスごとの state を使う例は、どれも空間を混ぜる部品を別に持っている**（AUSM と イベントカメラ：attention、TV3S：shift、ConvS5：畳み込み、Long-Context：局所 attention）。動きに合わせて state を運ぶ例はない。
- 因果的な設定でシリアルと並列を直接比べたのは、Long-Context の Table 5 だけ。位置合わせなしの並列（ブロックの大きさ1）が最低だった。

### 2.4 マスごとの state を動きに合わせて運ぶ案に関係するもの

| [PSRT](https://arxiv.org/abs/2207.08494)（NeurIPS 2022） | 双線形の再標本化は4画素の重み付き平均で、1画素未満の情報が失われる。パッチごとに、flow の端数を捨てて動かす（再標本化しない） | 確認済み |
| [Mentzer ら](https://arxiv.org/abs/2107.12038) | 0.5 画素ずつ20回ずらす実験で、補間の核によるぼけを比べている（図）。"To avoid blurry results when repeatedly warping, the quality of the resampling kernel is crucial" | 確認済み |
| [VSRM](https://arxiv.org/abs/2506.22762)、[MambaVSR](https://arxiv.org/abs/2506.11768) | Mamba の動画超解像。特徴を位置合わせしてから Mamba で集める。state 自体は運ばない | 確認済み |

- **Mamba の hidden state を flow や対応で運ぶ先行例は、見つからなかった**（11/2 サーベイの「カテゴリ5に、state を明示的にワープした一次資料は見つからなかった」と同じ結果）。
- 位置合わせの spec の「端数をマスごとに持ち越す」案を明示した論文も見つからなかった。近いのは PSRT（端数を捨ててパッチごと動かす）。

## 3. 今日の計測：state は何ステップ残るか（CPU、重みの読み取りだけ）

[実験ログ](../../../lab/projects/sam2-mamba-motion-tracking/experiments/2026-11-17-mamba-state-time-constants.md)。学習済みの V3（条件A、22 epoch）と A-b（22 epoch）の重みから、1ステップで state が残る割合 exp(−dt·|A|) を計算した。dt は bias の分だけで、入力に依存する分は入れていない。

- **時定数は初期値からほぼ動いていない。** `A_log` と初期値の差は平均 0.003〜0.013。2→22 epoch で `A_log` 0.8%、`dt_proj.bias` 0.6% の変化（同じ間に `in_proj` などは 63〜71%）。
- **半減期は中央値 約11ステップ**（10% 点 1.3、90% 点 約75、最大 約700）。段や A-b かどうかでほぼ変わらない。

| 何ステップ先か | 平均で残る割合 | 半分以上残る成分 | 最大 | 当てはまる案 |
|---|---|---|---|---|
| 1 | 0.86 | 94% | 0.999 | 並列の1フレーム |
| 16 | 0.39 | 41% | 0.985 | ブロック 4×4 の1フレーム |
| 64 | 0.16 | 12% | 0.94 | シリアルで縦の隣まで（64段の1行） |
| 100 | 0.11 | 7% | 0.91 | マスク内シリアルの1フレーム（DanceTrack の人物の box 程度） |
| 256 | 0.036 | 1.8% | 0.79 | 16×16 に縮めた画面の1フレーム |
| 4,096 | 0.0001 | 0% | 0.02 | 全体シリアルの1フレーム（64段） |
| 65,536 | 0 | 0% | 1e-27 | 全体シリアルの1フレーム（256段） |

読み取り

- 並列の V3 は、重みの上では数フレーム〜数十フレームの記憶を持てる。「state がすぐ消えるから寄与が0」では説明できない。
- **全体シリアルで state を次のフレームへ渡しても、今の初期値と学習の進み方のままでは、前のフレームはほぼ届かない。** 実質は「フレーム内の空間を混ぜる Mamba」になる。届かせるには、dt の初期値を2桁ほど小さくするか、入力に依存する分で dt を0近くに下げることを学習する必要がある。
- シリアルの1行先（縦の隣）でも、半分以上残る成分は 12%。LocalMamba・Spatial-Mamba の「縦の隣が遠い」と合う。
- 限界：入力に依存する dt は未計測（`dt_proj.weight` は 33% 動いている）。シリアルの値は、並列で学習した重みの時定数を当てはめた計算。単一 seed。

## 4. メモリと計算の見積もり

V3 の設定（内部のチャネル＝入力の2倍、`d_state` 16、`d_conv` 4）での計算上の値。実測と書いたもの以外は測っていない。

**先生の指摘（11/13）の確認**

- 「4,096マス × 768次元を1つの状態ベクトルとして扱う」＝画面全体を1つのトークンにする場合。入力の次元は 256ch で約105万、768ch で約315万。
- このとき載らないのは**重み**。入力の射影だけで、256ch で約 4.4×10¹² 個（FP32 で 17.6 TB）、768ch で約 4.0×10¹³ 個（158 TB）。
- state 自体は、256ch で約4,200万個。並列（マスごと）の state と同じ数になる。**並列は、「画面全体を1つの state にしたもの」の重みを、マスごとに同じ小さな行列に制限した形**と言える。
- だから現実の選択肢は、重みを共有したまま state を小さくする（シリアル）か、state を大きいまま持つ（並列）か、になる。先生の「シリアルが主流」は、この整理と合う。

**案ごとの state（次のフレームへ渡す量、1物体あたり）**

| 案 | 64段 | 128段 | 256段 | 3段の合計 | バイト（ssm は FP32、conv は bf16） |
|---|---|---|---|---|---|
| 並列（V3） | 4,194万 | 4,194万 | 8,389万 | 1億6,777万 | 約576 MiB（64段だけなら約144 MiB） |
| ブロック 4×4 | 262万 | 262万 | 524万 | 1,049万 | 約36 MiB |
| 全体シリアル・マスク内シリアル | 10,240 | 2,560 | 1,280 | 14,080 | 約50 KiB（スキャン方向を増やすと、その倍） |
| 窓（K＝8、64段の特徴を保存） | 839万 | ― | ― | ― | 約16 MiB（bf16） |
| 端数の持ち越し（並列に足す分） | 8,192 | ― | ― | ― | 無視できる |

- 並列の state は物体の数に比例する。10物体なら3段で約5.6 GiB、64段だけで約1.4 GiB。DanceTrack のように人数が多い場面で効いてくる。
- **128段・256段が、並列の state の 3/4（約432 MiB／物体）を占める。**

**学習時の VRAM（実測、8フレーム、バッチ1。[実験ログ](../../../lab/projects/sam2-mamba-motion-tracking/experiments/2026-10-27-temporal-mamba-short-clip-official-trainer.md)）**

| 条件 | VRAM のピーク |
|---|---|
| A（V3、checkpointing なし、RTX PRO 4500） | 約22 GB |
| A（V3、checkpointing あり、RTX A4000） | 約9 GB |
| B（Mamba なし、RTX A4000） | 約4 GB |

- 並列の V3 は、学習でも Mamba なしより 5〜18 GB 多く使っている（計測の条件はそろっていないので目安）。A-b の輸送はさらに約1.0〜1.3 GB。
- Mamba-ND も、系列を多く分けるほどメモリが増えると報告している（80GB 対 17GB）。**「並列はメモリを食う」は、文献とも手元の実測とも合う。**
- シリアルの学習時のメモリは未計測。公式実装は、逆伝播用の途中の state を間引いて保存する作り（`selective_scan_interface.py` の `scan_intermediates`。間引きの間隔は確かめていない）なので、並列より小さくなる見込み（推論）。

**計算**

- 1フレームで Mamba に通すマスの数は、並列も全体シリアルも同じ（64段で 4,096）。違うのは、並列は全マスを同時に1歩、シリアルは 4,096 歩を順に進めること。256段では 65,536 歩。速度は未計測。
- マスク内シリアルは、マスクの面積ぶんだけで済む（DanceTrack の人物の box は中央値 5.5×18 マス）。

## 5. 位置合わせの設計が、そのまま使えるか

位置合わせの spec の部品は3つ。対応の重み W で state を運ぶこと、1マス未満の動きの端数をマスごとに持ち越すこと、対応する元が分からないマスの信頼度 c(p)。

| 案 | W で state を運ぶ | 端数の持ち越し | 分からないマスの信頼度 |
|---|---|---|---|
| **並列** | そのまま使える（設計の前提） | そのまま使える | そのまま使える。弱める・初期化する相手（そのマスの state）がある |
| **フレーム内シリアル＋並列** | 時間の側が並列なので、そのまま使える。順番は「運ぶ → 時間の1歩 → 空間を混ぜる」 | 同左 | 同左 |
| **ブロック** | そのままは使えない。ブロック単位の移動に作り直す。ブロックより小さい動きは、ブロックの中で吸収される | ブロック単位に置き換える | ブロックごとの平均に置き換える |
| **全体シリアル** | 運ぶ相手（マスごとの state）がない。使うなら、前フレームの特徴を W で運んで現フレームのトークンに足す形に変える（state ではなく入力の位置合わせ） | 当てはまらない。入力を毎回元の特徴から運ぶなら、補間は累積しない。ただし1フレーム前しか見ない | 入力のチャネルとして渡すことはできる。state の側に受け皿はない |
| **マスク内シリアル** | 要らない。マスク基準の並びが、物体の平行移動を吸収する。回転・変形・部分的な遮蔽は吸収しない | 当てはまらない。1マス未満の動きは、境界のマスが入れ替わる形で現れる | 当てはまらない。遮蔽が解けたマスは、新しいトークンとして系列に入るだけ。代わりに、マスクの誤りがそのまま系列の誤りになる |
| **窓** | 使える。ただし W は隣り合うフレームの対応なので、k フレーム前から運ぶには、W を掛け合わせる（誤差とぼけが累積）か、t と t−k の対応を直接取る（探索の窓 ±7 マスを超えると取れない） | 要らない（state を繰り返し運ばない） | 使える（フレームとマスごと） |

- 位置合わせの spec が**そのまま**使えるのは、並列と、時間の側を並列にした組み合わせだけ。
- 並列＋位置合わせに固有の弱点もある。シリアルや窓にはないもの。
  - 繰り返し運ぶと state がぼける（Mentzer ら、PSRT。11/16 の見積もりでは 0.18 マス/フレームで 20フレーム後に標準偏差 約1.7 マス）。
  - 遮蔽で、たまった情報が失われる（FRVSR）。
  - 対応の誤りが state に入る（11/4 サーベイの MVSSM：flow の精度がそのまま性能に出る）。

## 6. ユーザーの仮説の検討

仮説：「位置合わせをするなら並列のほうが向く。シリアルにすると位置の情報がなくなる」

**成り立つ部分**

- 位置合わせの spec の3部品は、マスごとの state を前提にしている（5.）。全体シリアル・マスク内シリアルには置き場がない。
- 全体シリアルでは、同じマスの前フレームの情報は 4,096 ステップ前にある。今の時定数では届かない（3.）。マスごとの記憶は持てない。

**言い直しが要る部分**

- 上の1点目は、「位置合わせの設計が並列を前提に作られた」ことの言い換えに近い。並列の方が性能が良い、という証拠にはならない。
- 「位置の情報がなくなる」は不正確。現在のマスがどこにあるかは、位置埋め込みで渡せる（Vim、PlainMamba。SAM2 にもデコーダ用の位置符号化がある）。なくなるのは次の2つ。
  - マスごとの記憶（前のフレームの、同じ場所・同じ物体の点の情報）。
  - 縦の隣との近さ（LocalMamba、Spatial-Mamba）。
- 並列の側も、Mamba の中に位置の情報はない。全マスで同じ重みを使い、隣を見ない。位置を持っているのは「どのマスの state か」という置き場所だけ。

**反例と、条件つきで成り立つ場合**

1. **位置合わせをしないなら、並列はシリアルより悪い。** Long-Context の Table 5 で、並列（ブロックの大きさ1）は SSIM 0.766、シリアル 0.845。**論文が挙げる理由は「空間の相関を失う」ことで、動きによるずれではない**（"sacrifices spatial correlations, resulting in poor performance on the reasoning task where temporal retrieval alone is insufficient"）。state が場所に結び付いていると視点が動いたときにずれる、というのは私の推測（追記 16:40 で訂正）。手元の結果（A − A-reset1 ＋0.19 [−0.44, ＋1.00]、A' −0.03 [−1.32, ＋1.23]）と同じ向き。
   - ただし、タスクは動画生成で、局所 attention を併用している。追跡で成り立つかは分からない。
2. **マスク内シリアルは、位置合わせなしで平行移動を吸収する。** 並びが物体基準になるため。DanceTrack は1フレーム差でマスの 92% が1つの平行移動で合う（11/16 の予備計測）ので、理屈の上では相性がよい。
3. **窓の案なら、位置合わせとシリアル（軌跡に沿って時間方向に読む）が両立する。** TS-Mamba の形。このとき「軌跡ごとのシリアル」は並列と同じもの。
4. **系列を分けるほど悪くなる報告がある。** Mamba-ND（行動認識）：分けない 59.0、時間・空間に分ける 44.5〜55.8。VideoMamba の temporal-first が最下位なのは、1本の系列の並べ順の話で、並列とは別物。逆の報告もある（Video Mamba Suite：時間だけ 29.2 対 時空間 28.9）。
5. **目的が変われば、結論が変わる。** 持たせたいのが「物体の形・部分ごとの記憶」ならマスごと。「画面全体の文脈」や「物体の要約」なら、シリアルで足り、位置合わせは要らない。11/13 MTG でユーザーが言った目的は「画像全体の表現に時系列情報を組み込みたい」で、前者に当たる。

**まとめ**：仮説は、「マスごとの記憶を、対応に沿って運ぶことを目的にするなら、並列」と言い直すのが正確。この目的を置く限り、シリアルは代わりにならない。一方で、「並列＋位置合わせ」が「シリアル（位置合わせなし）」より良いかは、まだ誰も示していない。

## 7. 場所ごとの決定（推奨）

場所の名前は 10/9 の a〜d に合わせた。

| 場所 | 今 | 推奨 | 理由 | 推奨が変わる条件 |
|---|---|---|---|---|
| **b. 対象別の特徴（64段、デコーダ入口）** | 並列＋A-b | **並列を維持** | 位置合わせの spec がそのまま使える。手法2の目的（形・部分の記憶）に合う。マスごとの state の先行例がある（TV3S、AUSM、イベントカメラの SSM）。state は約144 MiB／物体で載る | 位置合わせを入れても state の寄与が0付近のまま → 並列の根拠がなくなる。ブロックか全体シリアルの対照を前に出す |
| **d. 128段・256段** | 並列（運ばない） | **持ち越しをやめる方向で、先に診断** | state の 3/4 を占める。64段の1マスの動きは、256段では4マス。ずれが一番大きい段なのに、A-b は64段しか運ばない。64段だけ reset した評価はある（A' − A'-reset64 ＋0.14 [−0.87, ＋1.20]）が、128・256段だけ reset した評価はまだない | 128・256段だけ reset すると性能が下がる（区間が0を含まない）→ 持ち越しに意味があるので、64段の W を拡大して運ぶ案へ |
| **a. 全対象で共通の特徴（Memory Attention の前）＝画面全体** | なし | 入れるなら**シリアル（フレーム内）**。本線にしない | 物体によらないので、state は動画に1つで軽い。ただし 4,096マス先の前フレームには届かず、時間方向の情報は入らない見込み。フレーム内の空間の混合は、画像エンコーダの attention と役割が重なる。V1（1 token を持ち越す）が効かなかったのも同じ向き | 16×16 に縮めれば前フレームに一部届く（半分以上残る成分 1.8%、最大 0.79）。「場面全体の動き」を持たせる動機が出たら、対照として1本 |
| **c. デコーダの内部** | なし | 入れない（10/9 の判断のまま） | ― | ― |
| **物体ごと（物体トークン、手法1）** | 手法1（box の系列を物体ごとに読む） | そのまま | 1物体1系列で、すでに時間方向のシリアル。マスク内シリアルは、この欄の別案に当たる | ― |

**先生の例（11/13）との対応**

- 「デコーダーの最初（画面全体）はラスタースキャン」→ 場所 a。シリアルにするのは妥当。ただし、今日の計測では時間方向の記憶にはならない。
- 「物体が決まった後は、物体領域だけをラスタースキャン、または並列」→ 場所 b。位置合わせを進めるので並列。物体領域だけのラスタースキャンは下。

**「SAM2 のマスクの部分だけ取り出してシリアルに入れる」案への答え（案）**

- 何になるか：物体ごとに1本の state（約1万個）。11/13 の表の「物体ごと × 対応を取らない」の欄。
- 良い点
  - 物体の平行移動を、位置合わせなしで吸収する。
  - 系列が短く（数十〜数百マス）、前のフレームに一部届く（100ステップ先で、半分以上残る成分 7%）。
  - メモリと計算が最小。
- 困る点
  - マスクが先に要る。デコーダ入口では、現フレームのマスクはまだない。前フレームのマスクを使う（手法1の予測で動かす）か、デコーダを2回通す。
  - マスクの形が変わると並びが変わる。学習時からその並びなら動く例はある（DyVM）が、並びがずれると落ちる例もある（Token Pruning、MAP）。位置の手がかり（物体基準の位置埋め込み）が要る見込み（PointMamba など）。
  - 役割が、SAM2 の object pointer・手法1と重なる。object pointer は MOSE dev で ±0（SAM2 論文 Table 11、11/2 サーベイ）。手法2で持たせたい「形・部分の記憶」は持てない。
  - 先行例は確認できていない。
- 判断：今は作らない。位置合わせ（並列）で state の寄与が出なかった場合の次の候補、または修論で「物体ごと」の欄を埋める対照にする。

### 1. A_log が初期値からほぼ動いていない原因

詳細は [実験ログの追記](../../../lab/projects/sam2-mamba-motion-tracking/experiments/2026-11-17-mamba-state-time-constants.md)（「追記 16:45」）。

- **0.8% は見かけの小ささ。** A_log の値は約2なので、相対で見ると小さく出る。Adam の1歩の大きさで測ると、他のパラメータと同じ程度に動いている。ただし、どのパラメータも向きのそろわない酔歩に近い。
- **学習率・重み減衰・グループ分けは原因ではない。** A_log は adapter の学習率のグループで、重み減衰は 0（公式実装と同じ扱い）。学習率の合計は、時定数を何倍にも変えられる大きさ。
- **原因は、時定数を動かす向きの勾配が出ていないこと。** 8フレームの区間ごとの勾配の向きは、学習の初めも終わりもばらばら（向きのそろい方 0.09〜0.23、ばらばらなら約 0.125）。8フレームの中では、持ち越した state から来る分は Mamba の出力の 2.5% 以下（64段）で、時定数を変えても損失がほとんど変わらない。
- **遅い成分ほど、Adam の eps で更新が弱められている。** A_log の勾配は成分の速さにほぼ比例し、半減期が長い成分ほど勾配が eps（1e-8）を下回る。半減期 32〜128 ステップの成分は、本来の 11% しか動けない。勾配を全体で 0.1 に切りそろえる設定（SAM2 の公式の学習設定）で、勾配が約 1/17 に縮められてから Adam に入ることも効いている。
- **dt の入力による変化も小さい。** 実際の dt は bias だけの値の 0.65〜1.6 倍（64段）、128段・256段はほぼ一定。時定数は、学習でも入力でも、初期値のまま。
- **Mamba では普通か。** 公式実装は、A_log・D・dt の bias を重み減衰から外すだけ。Mamba の論文は、言語モデルでは A の初期値の違いは小さく（Table 8）、選択的なパラメータの中では Δ が最も効く（Table 7）と報告している。学習後の A や Δ が動くかを調べた報告は、今回は確かめられなかった（下請けの調査が利用の上限で止まった）。
- **state の寄与がほぼ0だったこととの関係（私の読み）。** どちらも「8フレームの学習では、持ち越した state が損失にほとんど効かない」ことから出た結果と見ている。A_log が動かないことが寄与0の原因、という向きではない。
- **新しく分かった、学習と推論のずれ。** 推論（長い動画）では、持ち越した state から来る分が 64段で 13%、128段で 35% まで育つ（64フレーム以上）。学習は8フレームまでなので、この大きさの state は学習で見ていない。

**設計への意味（私の読み）**

- 位置合わせで state を正しく運んでも、学習が8フレームのままだと、state を使う向きの勾配は弱いままの可能性がある。位置合わせの spec の段階3（Mamba の学習）で、区間の長さ（16フレーム以上）を一緒に考える必要がある。10/23 MTG の「うまくいけば16フレーム以上に延ばす」と同じ方向。
- 時定数を学習で動かしたいなら、Adam の eps を小さくする、A_log と dt の bias の学習率を上げる、時定数の初期値を長い側に寄せる、が候補。どれも試していない。
- これらは位置合わせの spec の外の話なので、spec を書くときに別の項目として扱う。
