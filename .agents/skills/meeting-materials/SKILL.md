# Meeting Materials（MTG資料スキル）

MTG資料は、次の2段階で作る。

- **記録モード（作業のたび）**: 作業が一区切りしたら、その進捗だけを書いたエントリを `materials/entries/` に1ファイル作る。
- **仕上げモード（MTG直前）**: たまったエントリを1つの資料にまとめ、並べ替え、削り、相談を整えて、話せる資料にする。

直前に1週間分のログを読み直して長い報告書を作り、それを削って貼り直す、という作り方はしない。

## なぜこの形にしたか

2026年2〜11月のMTG記録を見直した結果、次のことが分かった。

- スキルを使わずに作っていた頃（3〜6月）の資料は1〜3K字で、話しやすかった。形は「トピック → 何をしたか → 図 → 分かったこと1〜3行 → 気になること」。
- 長い報告書型の資料（20〜36K字）を作るようになってから、ユーザーは毎回それを8〜12K字に削り、上の形に組み替えて貼っていた。
- 実験ログの記号（F0、A、A'、reset1、M0/M1 など）をそのまま資料に持ち込んだため、先生が「F0は何か」「何のグラフか」と確認するのに時間を使った（2026-10-30）。
- 2026-11-06のMTGでは、次のことが起きた。中身の違う手法を同じ形の図で並べて伝わらなかった。7×7を「周りの6マス」と説明して通じなかった。パラメータの根拠を答えられなかった。計画外の案を理由なく出した。結果として、相談事項の半分を扱えなかった。

そのため、資料の形はユーザーが話しやすい形に合わせ、MTGで口に出さないものは仕上げで削る。分量・図・相談の数に上限は設けない。

2026-11-13のMTG後の振り返りで、次のことが分かった。

- 資料は前回までより短く、話しやすく、手直しも少なかった。
- ただし、1つの資料ファイルに作業のたびに追記する形（記録中の資料と「記録メモ」の宿題チェックリスト）では、ほかの進捗が目に入り、今の作業に集中しづらかった。

そのため、エントリは進捗ごとに別ファイルにし、MTG直前にだけ1つにまとめる。前回の宿題との照合も、作業中ではなくまとめるときに1回だけ行う。

## エントリの形

保存先（進捗1つにつき1ファイル）:

```text
.research/lab/projects/<project>/materials/entries/YYYY-MM-DD-<topic>.md
```

- 日付は **作業した日**にする。
- 1ファイルには1つの進捗だけを書く。ほかの進捗のことは書かない。

frontmatter:

```yaml
---
date: YYYY-MM-DD          # 作業した日
project: <project>
type: mtg-entry
status: pending           # pending（未使用） → used（資料にまとめ済み）
used_in: null             # まとめた資料のパス（仕上げで書く）
---
```

本文は、資料の1トピック分と同じ形にする（下の「資料の形」の `## <トピック>` から相談まで）。前回の宿題への答えなら、本文の最初の行に「前回の宿題『<議事録の次やることの文言>』への答え」と書く。図のパスは、エントリの場所から見た相対パス（`../../experiments/figures/...`）にする。

## 資料の形

保存先:

```text
.research/lab/projects/<project>/materials/YYYY-MM-DD-weekly-progress-mtg-materials.md
```

- 日付は **MTGの日**にする（作業した日ではない）。
- 資料ファイルは仕上げモードで初めて作る。作業中には作らない。
- 週次以外の単発の相談資料は `YYYY-MM-DD-<topic>-mtg-materials.md` にし、同じ形で書く。

frontmatter:

```yaml
---
date: YYYY-MM-DD          # MTGの日
project: <project>
type: meeting-materials
status: ready
target_meeting: YYYY-MM-DD
previous_meeting: YYYY-MM-DD
entries: []               # まとめたエントリのパス
notion_url: null
notion_export: null
tags: [meeting-materials, research]
---
```

本文（Notionの「やったこと／次やること」にそのまま貼れる形）:

```markdown
# やったこと

## <トピック>

- 何をしたか（1行）

![](../experiments/figures/<dir>/<file>.png)

- 分かったこと（結論を先に書く）
    - 根拠の数字（何と比べた値か・単位を添える）
- 気になること・まだ分からないこと
- 詳細: [実験ログ](../experiments/YYYY-MM-DD-<topic>.md)
- **→ 相談：<XとYのどちらがよいか>**（必要な相談があるトピックだけ）

## <次のトピック>

...

# 次やること

- ...

# 研究外の連絡

- ...（ある場合だけ。必ず最後に置く）
```

書き方の約束:

- 箇条書きと短い文で書く。ユーザーが自分で書いていたNotionのメモに近い言葉にし、報告書の文体にしない。
- 相談は、そのトピックの末尾に太字の「→ 相談：」で置く。冒頭に相談の一覧は作らない。
- 相談は、必要なものだけ入れる。先生に決めてもらわないと次に進めないもの、方針が分かれていて先生の判断がほしいものに限る。すべてのトピックに相談を付けない。報告だけのトピックで構わない。「この扱いでよいか」のような、自分で決めて進められる確認は相談にしない（2026-11-13のMTGで、「A-aをA-bの改善の比較相手として扱う形でよいか（時間があれば）」は不要だった）。
- 「Evidence／Interpretation／Ask」「言えること／言えないこと」などの章は作らない。ただし、観測した事実と推測は混ぜない。推測には「〜と見ている（未確認）」と書く。
- 細かい表、信頼区間の一覧、全条件の数字、コマンド、ファイル一覧は資料に入れない。実験ログへのリンク1行で済ませる。
- 図の枚数は決めない。難しい内容ほど図を増やしてよい。各図の直後に、その図から読み取ってほしいことを1行書く。既存の `experiments/figures/` の図を相対パスで参照し、コピーしない。
- 数字は、MTGで口に出すものを書く。数字には、何と比べた値か（「前回のモデルとの差」「stateを毎フレーム0に戻した場合との差」など）と単位を添える。表いっぱいの数字は貼らず、実験ログへのリンクにする。

## 記録モード

### いつ記録するか

ユーザーが「記録して」と言ったときに加えて、AIが次の作業を終えたときは、頼まれなくても記録する。

- 実験・評価の結果が出て、実験ログを書いた・更新した
- 実装が一区切りした（動いた、詰まった、方針を変えた）
- 前回MTGの宿題を片付けた
- 論文調査・原稿・発表準備が一区切りした
- brainstormで方針が決まった

ファイル名の変更、軽微な修正、途中経過だけの作業は記録しない。記録したら、最後の報告に「次回MTG用のエントリを作りました（<エントリのパス>）」と1行添える。

### 手順

1. 今日の日付を確認する。
2. `materials/entries/YYYY-MM-DD-<topic>.md` を作る（フォルダがなければ作る）。
   - 同じ進捗の続きで、同じテーマの `status: pending` のエントリがすでにあれば、そのファイルに日付付きの小見出しで足してもよい。別のファイルにしてもよい（仕上げで1つのトピックにまとめる）。
   - ほかの進捗のエントリや、前回の宿題の一覧は開かない。今の作業のことだけを書く。
3. エントリを書く。
   - 前回の宿題への答えなら、最初の行にそう書く（宿題の文言は最新の議事録の「次やること」から取る）。
   - 何をしたか → 図 → 分かったこと → 気になること → 詳細リンク の順。
   - 行数は決めない。MTGで口に出すことだけを書き、口に出さない詳細は実験ログに任せる。
   - 先生の判断が必要な相談があるときだけ「**→ 相談：**」を付ける。なければ付けない。

### エントリで守ること

- 記号は増やさない。新しい記号を作ってよいのは、資料の中で3回以上使うものだけにする。初めて出す箇所で、中身を括弧で書く。それ以外は「短い区間で学習したモデル」のように中身で呼ぶ。
- 実験ログの記号をそのまま持ち込まない。
- パラメータの値（大きさ・範囲・窓・温度など）は、実装と実験ログで確かめてから書く。根拠がない値は「仮に決めた」と書く。
- 用語は分野の標準に合わせる。「k×kのカーネル（k²マス）」「±rマスの窓」などを使い、「周りの何マス」のような独自の数え方はしない。
- 例として示す数値は、学習後の値か、初期値か、説明用の例かを書く。

## 仕上げモード

### 読むもの

- `materials/entries/` の `status: pending` のエントリ
- `meetings/` の最新の議事録（宿題、説明の仕方への指摘、先生が誤解した点、答えられなかった質問）
- 値の照合が必要なときだけ、エントリからリンクされた実験ログと実装

`experiments/` や `specs/` を全部読み直して資料を作り直すことはしない。`references/` は、ユーザーが指定したものか、議事録からリンクされたものだけ読む。

エントリがない、または足りない場合（記録し忘れた週など）は、前回MTG以降の日付の実験ログ・spec・brainstormから、記録モードと同じ形でエントリを作ってから仕上げる。このやり方に切り替える前の `status: recording` の資料ファイルが残っていれば、その中身をエントリとして扱い、その資料ファイルを仕上げる。

### 手順

1. **エントリを集める**: `status: pending` のエントリを読む。前回MTGより前の日付の `pending` があれば、今回の資料に入れるかユーザーに確認する。前回MTG以降の実験ログにエントリの抜けがないかも確かめ、抜けていればエントリを足す。
2. **前回の宿題と照らし合わせる**: 最新の議事録の「次やること」の各項目に、対応するエントリがあるかを表にしてチャットで見せる（表は資料に入れない）。対応するエントリがない宿題は、ユーザーに1つずつ確認する。
    - 途中まで進んでいる → 資料の「次やること」に「実装中」などと書く
    - 手を付けていない → 「次やること」に残す
    - やめた → 理由を1行書いて、関係するトピックに入れる
3. **1つにまとめる**: `materials/YYYY-MM-DD-weekly-progress-mtg-materials.md`（日付はMTGの日）を作り、エントリを `# やったこと` の下のトピックとして入れる。同じテーマのエントリは1つのトピックにまとめる。図のパスは資料の場所に合わせて `../experiments/figures/...` に直す。
4. **並べ替える**: 相談があるトピックを、判断がほしい順に前に置く。報告だけのトピックは後ろに置く。研究外の連絡は最後に置く。
5. **前回の宿題・誤解に答える**: 前回の宿題への答えや、誤解されたこと・答えられなかった質問への回答は、関係するトピックの最初の行に短く書く。
6. **手法の説明を整える**: 手法は「何をするか → なぜ（何の対照か、前回のどの方針か） → 制約 → パラメータの根拠」の順に書く。前回MTGで合意していない案を足した場合は、最初に目的を一言書く。目的を書けない案は、本題から外して最後に回す。
7. **相談を整える**: 相談は「XとYのどちらがよいか」の選択肢の形にする。選択肢が3つ以上なら小さな表にしてよい。相談の数は決めないが、必要な相談だけ残す。自分で決めて進められる確認や、なくても次の作業に困らない相談は削る。残した相談のうち、今日決めてもらわないと次に進めない相談を前のトピックに置き、次回でもよい相談には「（時間があれば）」を付けて後ろに回す。MTGで時間が足りなくなっても、大事な相談から先に扱えるようにするため。
8. **削る**:
    - 全体の分量は決めない。やった量が多い週は長くなってよい。基準は「MTGで口に出すか」で、口に出さないもの（話さない数字、確認のためだけの条件、途中の試行）を削る。
    - 記号の定義表が要るほど記号があるなら、記号を減らす。
    - 図は枚数でなく、話さない図（説明の流れで使わない図）を外す。
    - 根拠の数字は、話すときに使うものだけ残す。
9. **値を照合する**: 資料に書いたパラメータの値・学習するか固定か・根拠を、実装と実験ログで確かめる。当日メモや過去の資料とずれていたら実装に合わせ、ずれをユーザーに伝える。
10. **次やることを書く**: 次の1週間でやる予定を箇条書きで書く。
11. **仕上げる**: 資料のfrontmatterの `entries` にまとめたエントリのパスを書く。まとめた各エントリを `status: used` にし、`used_in` に資料のパスを書く。エントリのファイルは消さない。

### 完了報告

資料本文には入れず、チャットで次を渡す。

```markdown
MTG資料を仕上げました: <path>（エントリN件をまとめた）

相談（話す順）:
1. <トピック>: <相談>
2. ...

MTG前の口頭準備:
- 30秒説明（手法ごと）: 何をするか / なぜ / 制約 / パラメータの根拠
- 聞かれそうな質問と答え（3〜5個。例: その値の根拠は？ 学習しているか？ 何と比べたか？）
- 資料・当日メモ・実装のずれ: <あれば列挙。なければ「なし」>
- 話す順番: 相談のあるトピック → 報告だけのトピック → 研究外の連絡
```

## Notion反映モード

ユーザーが「Notionに反映して」「Notionに貼れるようにして」と言ったときだけ行う。資料の正本は `materials/` のMarkdownのまま変えない。

### 背景（2026-11-13に確認）

- 研究室のMTGページは `tamaki-lab` ワークスペースにあり、ユーザーはそこに**ゲスト**として参加している。NotionのMCPはゲストでは接続できないので、研究室のページに直接書き込めない。
- 接続しているのは個人ワークスペースだけ。そこに画像込みの下書きページを作り、ユーザーが全選択→コピーして研究室のページに貼る。こうすれば、ワークスペースをまたいでも図ごと貼れることを確認した。

### 手順

1. 資料のMarkdownから、frontmatterを除いた本文を取り出す。
2. 本文の `![](...)` の画像をすべて、個人ワークスペースにアップロードする。
   - 画像ごとに `notion-create-file-upload` を呼び、返された `upload_url` へ `curl -X POST -F "file=@<path>;type=image/png"` と `upload_headers` の `authorization` を付けて送る。200が返ることを確かめる。
   - 本文の画像の参照を `![](file-upload://<file_upload_id>)` に置き換える。
3. 本文の手元ファイルへのリンク（`[実験ログ](../experiments/...)` など）は、Notionからは開けないので、`` 実験ログ（`<ファイル名>`） `` のようにファイル名だけにする。リンクにすると `http://<ファイル名>` へ自動変換されてしまう。
4. 入れ子の箇条書きは、行頭のスペース4つをタブにする。
5. `notion-create-pages` で、`creation_mode: draft`（非公開）、タイトル「YYYY-MM-DD MTG資料（コピー用の下書き）」としてページを作る。
6. 作ったページを `notion-fetch` で読み込み直し、画像の数が本文の図の数と一致すること、表と入れ子が残っていることを確かめる。
7. 資料のfrontmatterの `notion_url` に下書きページのURLを書く。
8. ユーザーに下書きページのURLと、貼り方（本文をクリック→`Ctrl+A` を2回→`Ctrl+C`→研究室のページで `Ctrl+V`）を伝える。

同じMTGの資料を直したあとに頼まれた場合は、下書きページを作り直さず、変わった箇所だけ `notion-update-page` の `update_content` で直す。

## 図

- まず `experiments/figures/` の既存の図を使う。
- 説明用の概念図を新しく作るときは、`materials/figures/YYYY-MM-DD-<topic>/` に保存する。
- 図の直後に、図から読み取ってほしいことを1行書く。
- 軸ラベル・単位・凡例を省略しない。
- 中身の違う手法を、同じ形のブロックで並べない。どこに何を入れたか（入力側か、stateか、出力側か）の違いが、図の形として見えるようにする。
- 図の中の数値が、学習後の値か、初期値か、説明用の例かを書く。

## しないこと

- README、TODO、議事録、`references/` を更新しない。
- `meetings/` にMTG前の資料を保存しない。
- 頼まれずにNotionへ書き込まない。Notionへは、頼まれたときに「Notion反映モード」で個人ワークスペースの下書きへ一方向に写すだけにし、Notion側の変更を `materials/` へ取り込まない。`materials/` のMarkdownを正本にする。後日、NotionからexportされたMarkdownが `references/` に入っても、共有後の写しとして扱い、`materials/` の正本を削除・移動しない。
- 作業中に資料ファイルを作らない・追記しない。作業中に書くのはエントリだけにする。
- 仕上げ済みの資料ファイルを丸ごと上書きしない。直すときは該当箇所だけ直す。
- エントリを消さない。仕上げで使ったものは `status: used` にして残す。
- 研究結果や数値を捏造しない。実験ログにない数字は書かない。

## 困ったとき

- 対象プロジェクトが曖昧: `.research/lab/projects/*/README.md` のfrontmatterで候補を出して確認する。
- 次回MTGの日付が分からない: ユーザーに確認する。分からなければ「前回MTG＋7日」とし、報告で日付を伝える。
- 前回MTGより前の `pending` のエントリがある: 今回の資料に入れるか、もう不要かをユーザーに確認する。
- 議事録がない: 前回の宿題との照らし合わせは飛ばして進める。
- 仕上げた後にMTGの日付が変わった: 資料のファイル名とfrontmatterの日付を直し、エントリの `used_in` も直す。
