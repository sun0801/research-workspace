# V3に空間方向の混合を入れる（案②・②'）と、SAM2のmemoryを絞る評価（D2） Spec

## 目的

V3の64段のMambaに、空間方向の混合を入れた2つの版（②：読み書きの空間カーネル、②'：stateそのものを毎フレーム空間方向に混ぜる）を、条件A（V3だけ学習）と同じ設定で学習する。そして、学習したV3がstateの持ち越しを使うようになるかを調べる。

あわせて、評価にSAM2のmemoryを絞るオプションを加える。既存のcheckpoint（F0・A）で、memoryを絞るとMambaのstateが使われるか（D2）を診断する。②・②'も、memoryがそのままの条件と絞った条件の両方で評価する。

## 背景

- これまでの結果：条件A（V3だけ学習、22 epoch）は、F0を上回った（+1.51）。一方、A−A-reset1（推論時に毎フレームstateをリセット）は +0.19 [−0.44, +1.00] で、学習したV3はstateの持ち越しをほとんど使っていない。経過フレーム別に見ても、学習区間と同じ8フレームまでは、reset差がほぼ0（[11/2 brainstorm](../../../../secretary/notes/brainstorm/2026-11-02-cvpr-timeline-vs-architecture.md) の13:58の追記）。
- 今のV3では、各マスが独立した時系列stateを持ち、Mambaの中でマスどうしは混ざらない。物体が動くと、前フレームのstateは別の内容を指す（作業仮説）。
- [Deep Research（2026-11-02）](../papers/2026-11-02-deep-research-spatial-correspondence-mamba-state.md) は、次の2点を挙げている。
  - 反対仮説(a)：SAM2のmemoryがすでに時間方向の情報を担っていて、追加のstateと冗長。SAM2 Table 11で、memoryにGRUを足しても改善しなかった。
  - ConvS5型の空間の読み書きカーネル（案②）は、もっとも安く試せる対照。
- 2026-11-04にユーザーと決めたこと（同じbrainstormの「追記 2026-11-04 12:04」と、その後の相談）：
  - 研究として面白い主案は①-b（潜在空間の相関でstateを運ぶ）。②・②'は、その比較対象として先に実装・学習する。①-bのspecは別に作る。
  - D2は、先に進むための関門にしない。②の学習と並行して回す。
  - 評価には、memoryを絞る条件を加える。
- コードで確認したこと：
  - `MambaCell` は、学習でも1フレームずつstepで回している（並列scanを使っていない）。そのため、stateを空間方向に混ぜる操作（②'）に、並列scanの制約はかからない。
  - SAM2のmemoryは、実行時に `num_maskmem` を書き換えて絞ることができない。時間の位置エンコーディングが `maskmem_tpos_enc[self.num_maskmem - t_pos - 1]` で選ばれるため、番号がずれる（`sam2/modeling/sam2_base.py` 944行）。`max_obj_ptrs_in_encoder=1` にすると、`t_diff_max` が0になって0で割ることになる。評価専用のオプションが必要。
  - 条件Aは、RTX PRO 4500で、activation checkpointingなし（`A_v3_nockpt.yaml`）で学習した（約6時間、VRAM約22 GB）。

## 検証したい問い

- V3の64段に空間方向の混合を入れると、学習したV3はstateの持ち越しを使うようになるか。valのJ&Fは上がるか。
- 近くのマスを覗くだけ（②）と、stateそのものを空間方向に動かせる（②'）とで違いがあるか。
- SAM2のmemoryを絞ると、学習済みのV3（A）はstateを使っているように見えるか（D2）。

- H8'（stateの寄与の増加、主な判定）：valで (②−②-reset1) − (A−A-reset1) ＞ 0。

## 実験・実装内容

SAM2 repo（`/mnt/HDD10TB-2/aburatani/2025_03_aburatani_sam2`）で、`dev`（`30afc59`）から新しいブランチ `feat/spatial-mixing-adapter` を切って実装する。

### 1. ②：読み書きの空間カーネル（64段だけ）

64段の処理を、次のように変える。128段・256段は変えない。

```text
今のV3：  x = LN(特徴) → MambaCell → h → W_out → 残差
②：      x = LN(特徴) → 書き込み用の空間conv → MambaCell → h → 読み出し用の空間conv → h'
         h' を W_out の残差と、128段への上からのつなぎの両方に使う
```

- 書き込みと読み出しの空間convは、どちらもdepthwiseの k×k 2D conv（各チャネル独立、biasなし、padding は (k−1)/2 のゼロ埋め）にする。マップは [B, 256, 64, 64]。
- k=7を基本にする（各±3マス。書き込みと読み出しを合わせて±6マス、1024入力で約±96px）。最終的なkは、5の動きの測定から、下の「カーネルの大きさの決め方」で決める。この±2rは、追加した64段の2つのconvを通る経路での範囲で、モデル全体（エンコーダ、memory attention、上からのつなぎ）での情報の届く範囲の上限ではない。
- **恒等初期化**：重みを「恒等カーネル（中心だけ1）＋学習する差分Δ」の形にし、Δを0で初期化する。weight decayはΔにかかるので、学習で使わない部分は恒等に戻る向きに働く。初期状態の出力は、今のV3と一致する。
- `MambaCell` は変えない。

### 2. ②'：stateそのものを毎フレーム空間方向に混ぜる（64段だけ）

64段で、Mambaを1ステップ進める前に、前フレームのstateを空間方向に混ぜる。

```text
②'：  state_{t-1} → 空間conv（ssm_stateとconv_stateの両方） → MambaCell（x_t で1ステップ） → state_t
```

- ssm_state は [B·64·64, d_inner=512, d_state=16]、conv_state は [B·64·64, 512, 4]。
- **軸の並べ替え**：ssm_state は `[B,64,64,512,16] → [B,16,512,64,64] → [B·16,512,64,64]` とし、groups=512 の depthwise k×k 2D conv をかけてから逆の順に戻す。conv_state も、16を4に置き換えて同じようにする。これで、物体の軸と d_state・conv の窓の軸が混ざらない。
- **カーネルの共有**：カーネルは d_inner のチャネルごとに1つ持ち、d_state の方向、conv の窓の方向、さらに ssm_state と conv_state の間で共有する（パラメータは 512×k×k）。
- biasなし、padding は (k−1)/2 のゼロ埋め。
- **dtype**：空間convの計算は、ssm_state・conv_state ともFP32で行う。autocastは、この計算の範囲だけ無効にする。conv_state は、混ぜたあとに元のdtypeへ戻す。
- kは、5の動きの測定から、下の「カーネルの大きさの決め方」で決める（1フレームでstateが動ける距離は±(k−1)/2マス。届く範囲は時間とともに広がる）。
- 恒等初期化は②と同じ（恒等＋Δ、Δを0で初期化）。初期状態は今のV3と一致する。
- Δの中心の成分は、同じ位置のstateの保持率も変えられる。そのため、学習後にΔの中心の成分と、中心以外の成分を分けて記録する（解釈で使う）。
- ②の読み書きカーネルは入れない（②'の効果だけを見るため）。
- Δには符号・総和の制約を付けないので、繰り返しかけるとstateが増幅・振動する可能性がある。長い系列での安定性を、段階1b・段階4で確かめる。非負・総和1の混合や、恒等とのgateは代替案として残すが、表現力も変わるので、今回は採用しない（不安定が出たときに、ユーザーと相談して決める）。

#### 2b. ②'の改訂：L1正規化したカーネル（2026-11-04、段階1bの⑨の結果を受けて）

段階1bの⑨で、上の②'（制約なしの恒等＋Δ）は、300更新後の重みでssm_stateが12フレーム目あたりから1フレームごとに約2倍になり、20〜21フレーム目で非有限になった（[実験ログ](../experiments/2026-11-04-temporal-mamba-spatial-mixing.md)）。Δの中心以外の成分が小さい正の値で広く付き、カーネルの成分の合計（滑らかなstateに対する増幅率）が1を大きく超えたためと考えている（推論）。そこで、本学習に使う②'を次のように改める。

- カーネルを、d_inner のチャネルごとに K = (I + Δ) / ‖I + Δ‖₁ とする（‖·‖₁ は k×k の成分の絶対値の和）。
  - ‖K‖₁ = 1 なので、ゼロ埋めのconvは、どのノルムでもstateを大きくしない（Youngの不等式。∞ノルムでは ‖K∗s‖∞ ≤ ‖s‖∞）。Mambaの更新は、これに要素ごとの減衰 exp(ΔA)（1以下）をかけて入力の項を足すので、stateが指数的に増えることはなくなる。
  - Δ=0 のとき K = I（‖I‖₁ = 1 で割るだけ）なので、初期状態がAと一致する性質は変わらない。
  - 符号の制約は付けない（負の成分も使える）。その代わり、成分の大きさの合計が1に制限されるので、恒等から離れるほど中心の重みが小さくなる。
- それ以外（軸の並べ替え、共有、padding、FP32での計算、k=7、Δのweight decay）は、上の②'と同じ。
- ②（読み書きのカーネル）は、stateを繰り返し通らないので変えない。②はこの改訂の前に本学習を始めてよい。
- 制約なしの②'は本学習しない。⑨の結果は、「空間方向の混合を制約なしで再帰に入れると、8フレームの学習では見えない形で発散する」という所見として実験ログに残す。
- 改訂後の②'でも⑨で不安定が出た場合は、本学習に進まずに相談する。

### 3. 共通

- `build_temporal_adapter` に `adapter_type: v3_spatial`（②）と `v3_state_mix`（②'）を加え、k を引数にする。既存の `v3` の挙動は変えない。
- **条件Aとの一致**：新しいパラメータは、既存のV3のパラメータをすべて作ったあとに、乱数を使わずに作る（Δは0、恒等カーネルは固定のbuffer）。こうすると、同じseedでAと同じ初期値になる。プロンプトの乱数は更新ごとに設定し直しているので、各更新で見るクリップとプロンプトもAと同じになる。
- weight decay：Δには、Aの V3 と同じ設定（0.1）をかける。恒等に戻る向きに働く。
- 学習率など、それ以外の設定はAと同じ（V3 3e-4 → 3e-5、bf16、勾配のclip 0.1、24,662更新（22 epoch）、seed 123、val-25は学習前と2 epochごと）。
- 推論時の `reset_every_frame` と `reset_interval` は、②'では混ぜる前のstateを0にする（今と同じ意味）。

### 4. 評価にSAM2のmemoryを絞るオプションを加える

`sam2_base.py` と `training/mose_adapter_eval.py` に、評価専用のオプションを2つ加える。どちらも既定はオフにし、オフのときは今の出力と一致させる。

- `--max-mem-frames N`：プロンプトのフレーム（t_pos=0）以外のmemoryを、直近N枚だけにする。時間の位置エンコーディングは、元の `num_maskmem=7` のときの番号のまま使う（直前のフレームはt_pos=6）。
  - Nは0以上の整数。N=0はプロンプトのフレームだけ、N ≥ num_maskmem−1（=6）は制限なしと同じ。負の値はエラーにする。
  - 評価のmemoryのstrideは1（今の評価の設定）を前提にする。stride>1のときはエラーにする。
  - 標準の経路だけに入れる。samurai_modeでこのオプションを使った場合は、黙って無視せずエラーにする。
- `--no-obj-ptrs`：object pointerを、memory attentionに渡さない（プロンプトのフレームのものも含めて渡さない）。pointerがない場合の既存の経路（`num_obj_ptr_tokens = 0`）を使う。
- 評価の記録（manifest）に、2つのオプションの値を残す。
- 注意：M1ではobject pointerの履歴が残り、M2でも直前のフレームのmemoryとプロンプトのフレームが残る。D2は、SAM2の時間方向の情報を完全に取り除く実験ではない。

### 4b. 差の差の集計

今の `mose_adapter_summary compare` は、2条件の差だけを扱う。stateの寄与が増えたかを判定するため、差の差を集計するサブコマンドを加える（評価の段取りに合わせ、段階0aで入れる）。

- 動画vのJ&Fを J とし、モデルm、memoryの条件Mについて、stateの寄与を R_v(m,M) = J_v(m,M,持ち越し) − J_v(m,M,reset1) とする。
- 空間方向の混合でstateの寄与が増えたか：I_v(m) = R_v(m,M0) − R_v(A,M0)（mは②または②'）。M1でも同じように計算する。
- memoryを絞るとstateの寄与が増えたか：D_v(M) = R_v(A,M) − R_v(A,M0)（MはM1・M2）。
- 関係するすべての条件で同じ動画を一緒に再標本化し（動画単位のpaired bootstrap、今と同じ回数）、平均と95%区間を出す。別々に出した区間の上限・下限を引き算しない。
- 動画内で対象を平均し、動画を等しい重みで平均する（今のsummaryと同じ）。

### 5. 動きの測定と、物体の速さでの層別（GPU不要）

**動きの測定（カーネルの大きさを決めるため）**

1フレームあたりの移動量を、SAM2の入力（1024×1024）に縮めたあとのstride 16のマス単位で測る。縦横で縮める比が違うので、x・yそれぞれ換算する。正方形の窓で覆えるかに直接対応するので、移動量は max(|dx|, |dy|)（マス）とする。元画像の幅・高さは、系列ごとの実際の値を使う。

- MOSEのtrain：GTマスクの重心。
- DanceTrackのtrain：`gt.txt` のbboxの中心（20fps、1920×1080。1マスは元画像の横約30px・縦約17px）。
- 集計は、隣り合うフレーム（モデルに実際に入る1ステップ。フレーム番号が欠けている箇所は、その間を1ステップとして数える）の両方に対象が写っている組だけを使う。中央値・75・90・95パーセンタイルを記録する。
- この測定は近似的な目安として扱う。
  - マスクの重心は、遮蔽や変形でも動く。純粋な物体の移動とは区別できない。
  - MOSEのマスクの重心とDanceTrackのbboxの中心は、同じものを測る指標ではない。2つの比を、そのままフレームレートの違いの証拠にはしない。
  - 学習ではRandomAffineなどのaugmentationがかかる。拡張前のGTでの移動量は、学習の入力での移動量の近似である。
- 結果は実験ログに残し、スクリプトはSAM2 repoのgit管理下に置く。

**カーネルの大きさの決め方（測定の前に決めておく）**

P_MOSE、P_DT は、それぞれ1フレームあたりの移動量の90パーセンタイル（マス）とする。

- ②：P_MOSE と P_DT がどちらも6マス以下ならk=7。超える場合は、2r ≥ max(P_MOSE, P_DT) を満たす最小のrで k = 2r+1 とする（上限9）。
- ②'：k = 2⌈P_MOSE⌉+1（3以上7以下にする）。学習データのMOSEに合わせる。
- P_DT が P_MOSE の半分未満なら、②'は「DanceTrackでは、学習時より1フレームあたりの動きが小さい」ことを、DanceTrackで評価するときのリスクとして記録する（下の「リスク・懸念」）。
- 選んだkで、1フレームの移動の何%を覆えるか（②は±2r、②'は±r以内の割合）を、両データセットで記録する。上限（②は9、②'は7）に達して90パーセンタイルを覆えない場合も、その割合を併記する。
- ②と②'でkの決め方が違うので、②と②'の比較は、純粋な機構の比較とは呼ばない。

**物体の速さでの層別（探索的）**

- valの各対象について、上と同じ方法で1フレームの移動量を計算し、対象ごとの中央値で3つに分ける（下位・中位・上位）。
- 区切りは、GTだけから、結果を見る前に決めて記録する。
- 速さで層別した差を、動画単位のpaired bootstrapで出す。探索的な分析として扱う。

**範囲外**：DanceTrackでの評価そのものは、このspecに含めない。MOT用のパイプラインが必要なので、別のspecにする。

## 評価指標

- val（313対象）の動画平均J&F（J・Fも併記）。差は動画単位のpaired bootstrapの95%区間（`mose_adapter_summary compare`）。
- 評価はすべてRTX A4000。
- 主な指標の差の差：I（空間方向の混合によるstateの寄与の増加）、D（memoryを絞ったときのstateの寄与の増加）。定義は4b。
- 副次：学習中の ‖α·W_out(h)‖/‖特徴‖ の比（既存のログ）、Δの大きさ（恒等からどれだけ離れたか。②'は中心の成分と中心以外の成分を分ける）。
- ②'の安定性：長い系列での ssm_state・conv_state のRMS、最大絶対値、NaN/Infの有無（フレームごと）。

## 成功/失敗の判断基準

結果を見る前に、次のように決めておく。

次の3つを分けて判定する。

- **H8・H10（そのモデルでのstateの寄与）**：M0で R(②,M0)＝②−②-reset1（②'も同様）の95%区間の下限が0より大きければ、「そのモデルでは、stateを持ち越す方が性能がよい」とする。
- **I（Aに対するstateの寄与の増加、主な判定）**：M0で I(②)＝R(②,M0)−R(A,M0) の95%区間の下限が0より大きければ、「空間方向の混合を入れると、stateの寄与が増えた」とする。②'も同様。Aの区間が0を含み②の区間が0を含まない、というだけでは、この結論にしない。
- **H9・H10（総合的な性能）**：M0で ②−A（②'−A）の95%区間の下限が0より大きければ、性能が上がったとする。

D2（H11）は次のように読む。

- M1かM2で R(A,M) の95%区間の下限が0より大きければ、「memoryを絞った条件では、学習済みのV3のstateが性能に寄与している」とする。D(M)（M0からの増加）の区間が0を含まなければ、「memoryを絞るとstateの寄与が増える」とし、反対仮説(a)を支持する材料とする。
- M1・M2でも差が出なければ、「このcheckpointでは、memoryを絞ってもstateの性能への寄与を確認できなかった」とだけ読む。Aはmemoryがそのままの状態で学習したので、stateの使い方を学んでいなければ、推論時にmemoryを絞っても使えるようにはならない。冗長が主な原因ではない、という結論にはしない。
- M1・M2の推論は、学習時と違う条件（OOD）である。各モデルは同じ介入を受けるが、OODの影響の大きさまで同じとは限らない。

組み合わせの読み方（どれも探索的な解釈）：

- ②・②'がM0では差なしで、M1では差あり → (a)と作業仮説の両方が効いている可能性。memoryを絞った状態で学習し直すことを検討する。
- ②'だけで差あり → 「この実装・このk・このseedでは、②'の設計が有望」「stateの位置間の伝播が寄与した可能性がある」とまで読む。Δの中心の成分（同じ位置の保持率の調整）による改善の可能性も残るので、中心と中心以外のΔの記録を合わせて見る。機構を強く主張する段階では、中心だけを学習する対照を検討する（今回は必須にしない）。
- ②・②'ともどの条件でも差なし → 空間方向の局所的な混合では、stateの寄与を確認できなかった。①-b（明示的な対応）に進む。①-bでも差がなければ、(a)・(b)・(c)の診断に戻る。

共通の注意：

- 単一seed、探索的な比較として扱う。val（125動画）はF0の選択にも使った開発用のデータで、区間は動画のばらつきだけを表し、seed間の再現性は含まない。
- 比較の組・memoryの条件・速さの層が多いので、95%区間は個々の比較の区間で、全体をまとめた確証ではない。主な比較はM0のIとし、すべての結果を報告する。
- 「差なし」は同等であることの証明ではない。区間が0を含むときは、区間の幅も報告する。
- val-25は経過を見るためだけに使い、判断には使わない。
- M2での②・②'の評価は、D2で R(A,M2) か D(M2) の区間が0を含まなかった場合に追加する（追加分は探索扱い）。

## リスク・懸念

- 反対仮説(a)が強いと、M0では②・②'とも差が出ない。M1の結果と合わせて読む。
- ②の届く範囲は、追加したconvを通る経路では、時間によらず±2r（k=7なら±6マス、k=9なら±8マス）で止まる。速い物体には届かない。
- ②'では、stateを繰り返し混ぜるので、stateがぼやける（平滑化される）おそれがある。また、stateが空間方向に広がるので、背景のstateが物体に混ざる（contaminationが増える）可能性もある。
- ②'では、Δに符号・総和の制約がないので、stateが増幅・振動するおそれもある。たとえば、ある成分の減衰が0.99で、空間convの増幅率が1.02なら、積は1を超え、同じ状況が続けば増え続ける（実測ではなく、起こりうる例）。weight decayや勾配のclipは、推論時のstateが有界であることを保証しない。段階1bの⑨と段階4で確かめる。
- ②'がstateを動かす量は、MOSE（実効約5fpsと推定）の動きで学習される。DanceTrack（20fps、1系列600〜1200フレーム程度）では、1フレームの動きが小さく系列が長いので、stateが物体より速く広がり、ぼやけや背景の混入が強く出るおそれがある。これはkの調整では解決しにくい。実際の動きに合わせて対応を取る①-bは、フレームレートの違いの影響を受けにくいと考えている（推論）。
- ②'のVRAM：64段のssm_state（1物体・1ステップあたり約134 MB、FP32）はAにもある。増えるのは、空間convの入力の保持、出力、並べ替えのコピー、backwardの分。増える量は未測定で、段階1bの⑥で確かめる。
- memoryを絞った評価は、学習時と違う条件（OOD）。F0もAも同じように影響を受けるので、比べること自体はできる。ただし、絶対値は下がる見込み。
- 10/30 MTGの「開発中はMambaだけを10 epoch」とは違い、22 epochで学習する。11/2の10 epochの評価で、10 epochでは効果が見えにくかったことと、Aと直接比べられることが理由。checkpoint_10も保存されるので、10 epoch時点の比較もできる。
