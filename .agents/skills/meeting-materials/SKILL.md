# Meeting Materials（MTG資料スキル）

MTG資料は、次の2段階で作る。

- **記録モード（作業のたび）**: 作業が一区切りしたら、次回MTG資料に5〜10行のエントリを追記する。
- **仕上げモード（MTG直前）**: たまったエントリを並べ替え、削り、相談を整えて、話せる資料にする。

直前に1週間分のログを読み直して長い報告書を作り、それを削って貼り直す、という作り方はしない。

## なぜこの形にしたか

2026年2〜11月のMTG記録を見直した結果、次のことが分かった。

- スキルを使わずに作っていた頃（3〜6月）の資料は1〜3K字で、話しやすかった。形は「トピック → 何をしたか → 図 → 分かったこと1〜3行 → 気になること」。
- 長い報告書型の資料（20〜36K字）を作るようになってから、ユーザーは毎回それを8〜12K字に削り、上の形に組み替えて貼っていた。
- 実験ログの記号（F0、A、A'、reset1、M0/M1 など）をそのまま資料に持ち込んだため、先生が「F0は何か」「何のグラフか」と確認するのに時間を使った（2026-10-30）。
- 2026-11-06のMTGでは、次のことが起きた。中身の違う手法を同じ形の図で並べて伝わらなかった。7×7を「周りの6マス」と説明して通じなかった。パラメータの根拠を答えられなかった。計画外の案を理由なく出した。結果として、相談事項の半分を扱えなかった。

そのため、資料の形はユーザーが話しやすい形に合わせ、量は仕上げで絞る。

## 資料の形

保存先:

```text
.research/lab/projects/<project>/materials/YYYY-MM-DD-weekly-progress-mtg-materials.md
```

- 日付は **MTGの日**にする（作業した日ではない）。
- 週次以外の単発の相談資料は `YYYY-MM-DD-<topic>-mtg-materials.md` にし、同じ形で書く。

frontmatter:

```yaml
---
date: YYYY-MM-DD          # MTGの日
project: <project>
type: meeting-materials
status: recording         # recording（記録中） → ready（仕上げ済み）
target_meeting: YYYY-MM-DD
previous_meeting: YYYY-MM-DD
notion_url: null
notion_export: null
tags: [meeting-materials, research]
---
```

本文（Notionの「やったこと／次やること」にそのまま貼れる形）:

```markdown
# やったこと

## <トピック>

- 何をしたか（1行）

![](../experiments/figures/<dir>/<file>.png)

- 分かったこと（1〜3行。結論を先に書く）
    - 根拠の数字は1〜3個まで
- 気になること・まだ分からないこと
- 詳細: [実験ログ](../experiments/YYYY-MM-DD-<topic>.md)
- **→ 相談：<XとYのどちらがよいか>**

## <次のトピック>

...

# 次やること

- ...

# 研究外の連絡

- ...（ある場合だけ。必ず最後に置く）

---

## 記録メモ（仕上げで消す）

- 前回の宿題:
    - [ ] ...
- 記録したエントリ:
    - MM/DD <トピック>
```

書き方の約束:

- 箇条書きと短い文で書く。ユーザーが自分で書いていたNotionのメモに近い言葉にし、報告書の文体にしない。
- 相談は、そのトピックの末尾に太字の「→ 相談：」で置く。冒頭に相談の一覧は作らない。
- 「Evidence／Interpretation／Ask」「言えること／言えないこと」などの章は作らない。ただし、観測した事実と推測は混ぜない。推測には「〜と見ている（未確認）」と書く。
- 細かい表、信頼区間の一覧、全条件の数字、コマンド、ファイル一覧は資料に入れない。実験ログへのリンク1行で済ませる。
- 図はトピックごとに原則1枚。既存の `experiments/figures/` の図を相対パスで参照し、コピーしない。

## 記録モード

### いつ記録するか

ユーザーが「記録して」と言ったときに加えて、AIが次の作業を終えたときは、頼まれなくても記録する。

- 実験・評価の結果が出て、実験ログを書いた・更新した
- 実装が一区切りした（動いた、詰まった、方針を変えた）
- 前回MTGの宿題を片付けた
- 論文調査・原稿・発表準備が一区切りした
- brainstormで方針が決まった

ファイル名の変更、軽微な修正、途中経過だけの作業は記録しない。記録したら、最後の報告に「次回MTG資料に追記しました（<トピック>）」と1行添える。

### 手順

1. 今日の日付を確認する。
2. 対象プロジェクトの `materials/` から、frontmatterが `status: recording` のファイルを探す。
3. 見つからなければ作る。
   - 前回MTGの日付は、`meetings/` の最新の議事録から取る。
   - 次回MTGの日付は、ユーザーが言っていればそれを使う。分からなければ「前回MTG＋7日」とし、報告で日付を伝える。
   - 「記録メモ」の前回の宿題には、最新の議事録の「次やること」を写す。
4. エントリを書く。
   - 同じトピックの見出しがすでにあれば、その下に日付付きで足す。なければ `# やったこと` の末尾に新しい見出しを作る。
   - 長さは5〜10行。何をしたか → 図 → 分かったこと → 気になること → 詳細リンク の順。
   - 数字は、分かったことを支える1〜3個だけにする。
   - 相談したいことがあれば「**→ 相談：**」を付ける。なければ付けない。
5. 記録メモを更新する。片付いた宿題に `[x]` を付け、記録したエントリを1行足す。

### エントリで守ること

- 記号は増やさない。新しい記号を作ってよいのは、資料の中で3回以上使うものだけにする。初めて出す箇所で、中身を括弧で書く。それ以外は「短い区間で学習したモデル」のように中身で呼ぶ。
- 実験ログの記号をそのまま持ち込まない。
- パラメータの値（大きさ・範囲・窓・温度など）は、実装と実験ログで確かめてから書く。根拠がない値は「仮に決めた」と書く。
- 用語は分野の標準に合わせる。「k×kのカーネル（k²マス）」「±rマスの窓」などを使い、「周りの何マス」のような独自の数え方はしない。
- 例として示す数値は、学習後の値か、初期値か、説明用の例かを書く。

## 仕上げモード

### 読むもの

- `status: recording` の資料ファイル
- `meetings/` の最新の議事録（宿題、説明の仕方への指摘、先生が誤解した点、答えられなかった質問）
- 値の照合が必要なときだけ、エントリからリンクされた実験ログと実装

`experiments/` や `specs/` を全部読み直して資料を作り直すことはしない。`references/` は、ユーザーが指定したものか、議事録からリンクされたものだけ読む。

記録中のファイルがない場合（このやり方に切り替える前の週や、記録し忘れた週）は、前回MTG以降の日付の実験ログ・spec・brainstormから、記録モードと同じ形でエントリを作ってから仕上げる。

### 手順

1. **抜けを確認する**: 前回の宿題が、それぞれトピックか「次やること」に出ているか。前回MTG以降の実験ログにエントリの抜けがないか。抜けていればエントリを足す。
2. **並べ替える**: 相談があるトピックを、判断がほしい順に前に置く。報告だけのトピックは後ろに置く。研究外の連絡は最後に置く。
3. **前回の宿題・誤解に答える**: 前回の宿題への答えや、誤解されたこと・答えられなかった質問への回答は、関係するトピックの最初の行に短く書く。
4. **手法の説明を整える**: 手法は「何をするか → なぜ（何の対照か、前回のどの方針か） → 制約 → パラメータの根拠」の順に、1〜3行で書く。前回MTGで合意していない案を足した場合は、最初に目的を一言書く。目的を書けない案は、本題から外して最後に回す。
5. **相談を整える**: 相談は「XとYのどちらがよいか」の選択肢の形にする。選択肢が3つ以上なら小さな表にしてよい。資料全体で、相談は優先度の高い3つまで。4つ目以降は「（時間があれば）」を付けて後ろのトピックに回すか、削る。
6. **削る**:
    - 本文は3〜5K字を目安にする。超えたら、報告だけのトピックから削る。
    - 記号の定義表が要るほど記号があるなら、記号を減らす。
    - 図はトピックごとに原則1枚にする。
    - 根拠の数字は、話すときに使うものだけ残す。
7. **値を照合する**: 資料に書いたパラメータの値・学習するか固定か・根拠を、実装と実験ログで確かめる。当日メモや過去の資料とずれていたら実装に合わせ、ずれをユーザーに伝える。
8. **次やることを書く**: 次の1週間でやる予定を、箇条書きで3〜5個書く。
9. **仕上げる**: 「記録メモ」の節を消し、frontmatterを `status: ready` にする。

### 完了報告

資料本文には入れず、チャットで次を渡す。

```markdown
MTG資料を仕上げました: <path>（約N字）

相談（話す順）:
1. <トピック>: <相談>
2. ...

MTG前の口頭準備:
- 30秒説明（手法ごと）: 何をするか / なぜ / 制約 / パラメータの根拠
- 聞かれそうな質問と答え（3〜5個。例: その値の根拠は？ 学習しているか？ 何と比べたか？）
- 資料・当日メモ・実装のずれ: <あれば列挙。なければ「なし」>
- 話す順番: 相談のあるトピック → 報告だけのトピック → 研究外の連絡
```

## 図

- まず `experiments/figures/` の既存の図を使う。
- 説明用の概念図を新しく作るときは、`materials/figures/YYYY-MM-DD-<topic>/` に保存する。
- 図の直後に、図から読み取ってほしいことを1行書く。
- 軸ラベル・単位・凡例を省略しない。
- 中身の違う手法を、同じ形のブロックで並べない。どこに何を入れたか（入力側か、stateか、出力側か）の違いが、図の形として見えるようにする。
- 図の中の数値が、学習後の値か、初期値か、説明用の例かを書く。

## しないこと

- README、TODO、議事録、`references/` を更新しない。
- `meetings/` にMTG前の資料を保存しない。
- Notionへ直接同期しない。`materials/` のMarkdownを正本にする。後日、NotionからexportされたMarkdownが `references/` に入っても、共有後の写しとして扱い、`materials/` の正本を削除・移動しない。
- 資料ファイルを丸ごと上書きしない。エントリの追記と、仕上げでの並べ替え・削除で更新する。
- 研究結果や数値を捏造しない。実験ログにない数字は書かない。

## 困ったとき

- 対象プロジェクトが曖昧: `.research/lab/projects/*/README.md` のfrontmatterで候補を出して確認する。
- `status: recording` のファイルが2つ以上ある: どちらが次回MTG用かを確認する。
- 議事録がない: 宿題の欄は空にして進める。
- 次回MTGの日付が変わった: ファイル名とfrontmatterの日付を直す。
