# SAM2公式の学習コードによるtemporal Mamba（V3）の短い区間での学習 Spec

## 目的

SAM2の公式の学習コード（`training/train.py`・`trainer.py`・`SAM2Train`）を基盤に、V3を8フレームの区間で学習する。全軌跡で1周学習したV1・V3ではvalが伸びなかったので、学習方法を変えればvalが伸びるか、Mambaの効果が出るかを確かめる。あわせて、今後の拡張（16フレーム以上への延長、複数対象、空間方向の手法）の基盤を公式の学習コードに移す。

## 背景

- 10/23 MTGで、学習を軌跡全体のTBPTTから8フレーム程度の短い区間に切り替え、うまくいけば16フレーム以上に延ばす方針になった（SAM2の段階的な学習にならう）。まずまともに学習できるようにすることを優先し、空間方向とSAM2MOTへの組み込みは後にする。
- 全軌跡で1周学習した結果（[V3 実験ログ](../experiments/2026-10-18-temporal-mamba-v3-mose-adapter.md)）：V1はadapterが学習されていた（α=0.975、残差の比0.067）が、学習中のval（tuningの先頭25動画）はF0から−0.4〜+1.2ポイントで上下し、伸びる傾向はなかった。val全体（125動画・313対象）でも、F0 J&F 0.7701に対しV3 0.7698（V3−F0 −0.03ポイント、95%区間 [−0.72, +0.59]）、V3−V3-reset +0.13ポイント（[−0.18, +0.42]）で、どちらも改善は確認できなかった。V1でval-25に見えていた+0.5ポイント前後の差も、val全体では出なかった。
- 8フレームの区間にしても1フレームあたりの計算は変わらない（今もTBPTT=8）。1周で使うフレームが約1/9になり、同じ時間で更新回数とサンプルの多様性が増える。
- 自作の学習スクリプト（`training/mose_adapter_train.py`）はリファクタリングを終えた（[記録](../experiments/2026-10-23-mose-adapter-train-refactoring.md)、SAM2 repo `09a30a7`）。将来の拡張を楽にするため、学習は公式のコードに移す。自作スクリプトは過去のrunの再現用に残す。
- 相談の経緯：[brainstormメモ](../../../../secretary/notes/brainstorm/2026-10-26-temporal-mamba-short-clip-training.md)。

### 名前の対応

この spec では train / val / test と書く。コードと過去の記録の名前は変えない。

| この spec | コード・過去の記録 | 中身 |
|---|---|---|
| train | fit | SAM2のMOSE train listのうち1,121動画（2,789軌跡、`runs/mose_temporal_mamba_20260930/fit_trajectories.json`） |
| val | tuning | 同じlistの残り125動画（313対象、`tuning_trajectories.json`） |
| val-25 | 学習中のval | valの先頭25動画（64対象）。経過を見るためだけに使う |
| test | lockbox | SAM2のMOSE val list 200動画（570対象）。SAM2論文の「MOSE dev」と同じ。10/8に一度使用済み |
| MOSE公式valid | — | 311動画。CodaLabで採点。論文用 |

3つ（train・val・test）はどれもMOSE公式trainから取ったもの。配布されたSAM 2.1はMOSEで学習していない（SAM 2論文 D.2.2）。

## 検証したい問い

公式の学習コードで、8フレームの区間・1対象・先頭1枚のプロンプトでV3を学習すると、学習が進むにつれてvalが伸び、F0を上回るか。マスクデコーダも学習する条件で、V3はMambaなしの場合を上回るか。

## 仮説

- H1（学習方法、監視用）：Aでは、学習が進むにつれてval-25が上がる。val-25は25動画だけなので、H1は経過を見るための指標とし、効果の判定はH2・H3で行う。
- H2：valでA ＞ F0。
- H3：valでC ＞ B（マスクデコーダを学習する条件でのMambaの効果）。
- H4（診断）：A・Cの推論時のstateを、carry・8フレームごとにreset・毎フレームresetで比べ、持ち越しへの依存を見る。H2・H3の判定には使わない。

## 実験・実装内容

### 条件

すべてF0（`runs/mose_temporal_mamba_20260930/F0_step_002789.pt`）から始める。

| 条件 | V3 | 学習するもの | 固定するもの |
|---|---|---|---|
| A | あり（3段：64・128・256） | V3 | SAM2本体すべて |
| B | なし | マスクデコーダ（`sam_mask_decoder`） | それ以外のSAM2本体 |
| C | あり（3段） | V3＋マスクデコーダ | それ以外のSAM2本体 |

- 固定したmoduleはevalモード、学習するmodule（V3・マスクデコーダ）はtrainモードにする（今の学習と同じ扱い）。公式の `trainer` が `model.train()` を呼んでも、固定したmoduleのdropoutなどが有効にならないようにする。
- 「固定」は `eval()` と `requires_grad=False` のことで、勾配を止めることではない。V3の出力からlossまでの経路（Memory Attentionの後のマスクデコーダ、固定した場合も含む）には勾配が流れる。
- 画像エンコーダは公式の `freeze_image_encoder` で固定する。そのほかの固定は追加で実装する。
- A・Cでは、V3の `MambaCell` のactivation checkpointing（`adapter.set_checkpointing(True)`、既定は無効）を有効にし、configとmanifestに記録する。無効では1対象でも約21 GiB使い、A4000に入らない（V3 実験ログ）。公式の補正クリック用のcheckpointing（`use_act_ckpt_iterative_pt_sampling`、公式の設定は無効）とは別のものとして記録する。
- V1は実験から外す。

### 比較を公平にするための固定

- A・B・Cで同じ更新回数Nを使う。Nは学習を始める前に固定する（下の「学習量の2段階」）。Bが速いことを理由にBだけ更新回数を増やさない。
- 学習のseedを固定し、データ側の乱数（動画の順番、区間の開始位置、対象ID、augmentation、プロンプトの種類・座標）をモデルの初期化の乱数と分ける。A・B・Cで同じサンプル列になるようにし、実際に使ったサンプル列（動画、開始フレーム、対象ID、augmentationのパラメータ、プロンプトの種類）をrunごとに記録する。実装では、dataloaderのworkerを `seed + epoch` から初期化し、プロンプトの乱数（boxのノイズ、クリック）は更新ごとに `seed × 1,000,003 + step` で初期化し直す（記録はクリップの開始フレーム・対象・プロンプト・画像の合計値で、augmentationのパラメータそのものは残らない）。
- 補正クリックの座標は予測の誤りから取るので、条件ごとに変わりうる。これは条件の違いの一部として扱う。

### 学習量の2段階

| | 短いスケジュール（段階3） | 公式の長さ（段階3b、条件付き） |
|---|---|---|
| 目的 | 約1日で、学習率を下げ切った結果を出し、区間を短くした学習が効くかを見る | 効果が見えた場合に、公式の学習量で本番の数値を出す |
| 1 epoch | trainの1,121動画から1区間ずつ（`multiplier: 1`） | 1,121動画×2区間（`multiplier: 2`、公式と同じ） |
| epoch数 | 22 | 40（公式と同じ） |
| 更新回数N | 24,662（≒20万フレーム。全軌跡で学習したV3の1周200,794フレームとほぼ同じ量） | 89,680 |
| 所要時間の目安（A・C） | 約18時間 | 約2〜3日 |
| 学習率 | N更新でcosineで1/10まで下げる | 同じ形でN更新 |

- 段階2の実測で、短いスケジュールが1日を大きく超える見込みなら、Nを見直してから始める。
- 段階3bはF0と新しいV3から学習し直す（段階3の重みは引き継がない）。段階3bに進むかは、段階4の後にユーザーと相談して決める。目安は、H2またはH3を支持する、あるいはそれに近い結果が出た場合。
- どちらの段階も、途中のval-25を見て「良さそうだから止める」ことはしない（valでcheckpointを選ぶことになるため）。

### 途中で止める条件（事前に固定）

次のどれかに当てはまったら、学習を止めてよい。止めたrunの重みは最終結果としては扱わず、「途中で中止」と記録する。

- lossが有限でなくなった、または発散した（固定したパラメータが変わった場合も含む）
- 段階3bで、半分（44,840更新）の時点のA・Cとも、最後の3回のval-25の平均がstep 0以下

### V3のstate

- 区間ごとに0で初期化したstateを明示的に作り、学習の経路に渡す。現コードでは `temporal_state=None` だと推論用（streaming）の経路に入る（`sam2_base.py` 1139〜1146行）ので、学習では必ず明示したstateを渡す。区間の中で1フレームずつ持ち越し、8フレームなので区間全体で1回backwardする（TBPTTの区切りはない）。区間の終わりでstateを捨て、次の区間に値や計算グラフを持ち込まない。
- 先頭フレームにGTマスクを与えた場合、SAM2はそのフレームのマスク予測にGTをそのまま使う（`use_mask_input_as_output_without_sam: true`、`sam2_base.py` の `_track_step`）。object pointerを作るためにマスクデコーダは呼ばれる（`use_obj_ptrs_in_encoder: true`、`_use_mask_as_output`）が、V3は通らない。公式の動きどおり、そのフレームではV3を通さず、初期化したstateをそのまま次のフレームに渡す。クリック・boxの場合は先頭フレームでもV3が動く。
- 評価で使うboxでは先頭でもV3が動くので、マスクを与えた学習とはstateの最初の履歴が1歩分違う。stateは再帰的に更新されるので、この違いは後のフレームにも伝わりうる。**後続への影響は未検証**。

### 記録

- Comet（`samurai-mot`、タグ `temporal-mamba`）に、学習のloss（内訳を含む）・学習率・勾配のノルム・val-25を記録する。
- runごとに、configのコピー、`manifest.json`、`git.diff` を保存する（今の `run_provenance` の形）。manifestには、実際に学習したパラメータ名と数、weight decayから除外したパラメータ名、学習率のグループ、固定したmoduleとそのモードを、実際のモデルから取って記録する（リファクタリングのR1と同じ考え方）。
- loss の推移は中央値も記録する（物体の消失・出現でlossが極端に大きくなる軌跡があり、平均は大きく揺れるため）。

### 補正クリックの経路の修正

先頭のクリック・boxで補正クリックを入れるので、旧自作trainer（`num_correction_pt_per_frame=0`）では通らなかった経路を使う。現コードには次の不整合があり、段階0で直す。

- `sam2_base.py` の `_forward_sam_heads` は8要素（`kf_ious` を含む）を返すが、`training/model/sam2.py` の補正の呼び出し元（426行付近）と `_iter_correct_pt_sampling`（518行付近）は7要素として受け取っている。このままでは補正に入った時点で失敗する。
- 通常の経路は全候補のIoU（`_last_multimask_ious`）をlossに渡す（405行）が、補正の経路は選択済みの1個のIoUを渡している。初回のクリックで3候補を出す場合、IoU lossが候補ごとの正解IoUと対応しない。補正の経路でも全候補のIoUを渡すように揃える。

### 学習済みの重みの保存と評価への受け渡し

- 公式の `trainer` は全重みを `checkpoint["model"]` に保存する（`trainer.py` 339〜349行）。今の評価ラッパー（`mose_adapter_eval.py`）は「F0を読み、adapterだけを足す」形なので、B・Cの学習済みマスクデコーダが反映されない。
- 凍結済みの `evaluate_track` はそのまま使い、その外側に、公式のcheckpointからSAM2本体（学習したマスクデコーダを含む）とV3（ある場合）を復元する評価用のloaderを新しく作る。復元は `strict=True` で行う。
- F0からの初期化では、新しく足すV3のパラメータ以外のmissing・unexpected keyを許さない。公式configの `strict: true` を全面的に外す形にはしない。

### val

- val-25：学習前と、2 epoch（2,242更新）ごと（最後を含む）に、checkpointを保存し、上のloaderで復元したモデルを凍結済みの `eval_mose_fulltrack.evaluate_track` でJ・F・J&Fを測る（リファクタリングのR5と同じ）。経過を見るためだけに使い、checkpointの選択や打ち切りには使わない。
- 最終評価には、最後の更新の重みを使う。

## 評価指標

- val（125動画・313対象）での動画平均J&F。JとFも併記する。差は百分率ポイントで示す。
- 差の判定は、動画単位のpaired bootstrap（V3 specと同じ方法）。
- 学習の経過はval-25のJ&F。

## 成功/失敗の判断基準

- H1（監視用）：最後の3回のval-25の平均が、step 0（F0、0.7811）より0.5ポイント以上高ければ「val-25で改善傾向あり」とする。満たさなければ「val-25では改善を確認できない」と述べるにとどめ、学習方法の失敗とは判断しない（val-25の差がval全体で再現しなかった前例がある）。
- 効果あり（H2・H3）：A−F0、C−Bのpaired bootstrapの95%区間の下限が0より大きい。
- 次に進む方針（16フレームへの延長、構造の変更、本体の学習範囲など）は、段階4の後に、H1〜H3と学習側の診断（学習lossの推移、V3の各段の重みの変化、残差の比）を合わせてユーザーと相談して決める。Bだけが伸びてCがBを上回らない場合は、Mambaの効果は確認できなかったと解釈する。
- 結果は単一seedの探索的な比較として扱う。valはF0のcheckpoint選択にも使っているので、独立した評価での優越性は主張しない。

### 段階1の確認項目

#### 初期化・データ・設定

- C1：初期化直後のA・Cの出力が、同じ基盤でV3なしと一致する（V3の出力層は0で初期化）。F0からの読み込みで、V3以外のmissing・unexpected keyがない。
- C2：学習に使う動画がtrainの1,121動画だけで、val・testの動画が入らない。同じseedでA・B・Cのサンプル列が一致する。
- C3：数回の更新の後、固定したパラメータは変わらず、学習するパラメータ・学習率・weight decayの除外・固定したmoduleのモード・V3のcheckpointingの有効化がmanifestと一致する。

#### 補正クリックとプロンプト

- C4：先頭のマスク・クリック・boxをそれぞれ強制し、forward・backwardが通る。クリック・boxでは補正クリックの経路に入り、各反復で候補ごとのIoUの予測と正解の形が対応している。
- C5：先頭にマスクを与えたときはV3を通らず、初期化したstateがそのまま次のフレームに渡る。クリック・boxのときは先頭でもV3を通る。

#### 時間方向の勾配

- C6：V3の出力層を0でない値にしたとき、後半のフレームのlossから、前のフレームのconv stateとSSM stateに勾配が届く（stateが途中で誤ってdetachされていない）。
- C7：区間と区間の間でstateがリセットされ、前の区間の値や計算グラフが次の区間に漏れない。
- C8：A・Cで、V3の各段のMamba・LayerNorm・出力層・段の間の1×1 convに勾配が届き、weight decay以外の理由で重みが変わる。

#### 学習と推論の経路の一致

- C9：補正クリックを無効にし、重み（V3の出力層は0でない値）・入力tensor・先頭のbox・初期state・区間の長さ・モード・精度をそろえたとき、学習の経路（`SAM2Train`）と推論の経路（`evaluate_track` のモデル）で、各フレームのマスクのlogitとV3のconv state・SSM stateが一致する。基準はV3 specと同じく、FP32・決定的な設定（`--deterministic`、math attention）で、ノルムに対する差1e-6以下。bf16は参考として差を記録する。前処理（正規化・解像度の変換）が二つの経路で違う場合は、その差を記録する。

#### 保存と復元

- C10：V3の出力層を0でない値にし、マスクデコーダを更新した状態（Cの場合。Bはマスクデコーダのみ）を公式の形式で保存し、評価用のloaderで別のモデルに復元すると、全パラメータと出力が一致する。
- C11：step 0のval-25が、保存済みのF0の値（0.7811）と一致する。

- 段階0〜1を終えたら、結果をユーザーに報告してから段階2に進む。
- 長時間のジョブは、Claudeがコマンドを用意し、ユーザーがtmuxで実行する。

## 期待される結果

- 次回のMTG（10/30ごろ）では、短いスケジュール（段階3）の結果を報告する見込み。実装と確認が予定どおり進めば、valでの評価まで出せる。遅れた場合は、val-25の学習曲線を報告する。
- 公式の学習コードの上でA・B・Cが回る状態になり、16フレームへの延長や空間方向の手法を同じ基盤で試せる。

## リスク・懸念

- 実装量が大きい（3〜4日の見込み）。ViEWの締切（10/30）と重なる。
- 公式の `trainer` は `torch.distributed` を前提にしている。1 GPUでの実行（`--num-gpus 1`）は公式でも想定されているが、Cometや固定したmoduleのモードの扱いで手を入れる必要がある。
- Aと全軌跡のV3の差には、区間の長さのほか、augmentation・プロンプト・サンプルの取り方の違いも入る。「学習方法一式を変えた効果」として扱う。
- 区間が短いので、長くstateを持ち越すこと自体は学習しない。推論時のstateの3条件の比較で、持ち越しの影響を確かめる。
- 公式のデータ読み込み・augmentationでは、正規化や解像度の変換が今の評価の経路と細かく違う可能性がある。段階1のC9は同じ入力tensorで確かめ、前処理の違いは記録する。
- 公式のlossはフレーム方向と補正の反復方向に合計するので、旧自作trainer（軌跡長で割る）よりlossと勾配のノルムが大きくなる。AdamWなので学習率が単純に何倍になるとは解釈しないが、勾配のclip（0.1）がかかる頻度は変わりうる。段階2のpilotで安定性を確かめ、clipがかかった割合を記録する。
- 補正クリックの経路は公式のコードでも今回初めて使う（旧自作trainerは通っていない）。段階1のC4で確かめる。

## 未決事項

- 短いスケジュールのN（24,662）は、段階2の実測で1日を大きく超える見込みなら見直す。
- 公式の長さ（段階3b）に進むかは、段階4の後に相談して決める。
- V3の学習率は段階2のpilotで確定する（3e-4、不安定なら1e-4）。
- 先頭のマスクでV3を通さないことによるstateの履歴の違いが、後のフレームに与える影響（未検証）。
