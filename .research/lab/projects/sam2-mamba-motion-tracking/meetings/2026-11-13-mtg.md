### optical flow（A-a）の結果の読み方

- 先生の指摘: 古典的なoptical flowは、設定した範囲（隣のピクセル程度）までしか探索しないので、画像上で1〜2ピクセル程度の動きでないと追従しない。MOSEの速い物体ほど大きく動いていれば、デフォルト設定で動かないのは当然 [3:43〜4:22]。
- 「手法が微妙だからうまくいかない」のではなく、パラメータ次第。デフォルト設定だとこうなる、ということを理解しないまま、**できないものを持ってきて「できません」と言っている**状態になっている、という指摘 [4:22〜4:49]。
- 図の説明不足: 輪郭線は正解マスク、矢印は物体領域内のflowの平均ベクトル。最初からそう説明すべき、という指摘 [2:12〜2:51]。
- 当日メモでのまとめ: optical flowは使い方（手法・設定）が悪いから性能が出ていないだけの可能性が高い。

### A-bの可視化への指摘

- 矢印の図（隣とのずれで青・オレンジに塗り分け）: 色の意味、閾値が本当に合っているかを問われた。ユーザーは結果だけを見ていて、正しく描けているかを確認していなかった [5:28〜6:43]。
- 解釈としては、RAFTは物体の中でも動きに沿った対応が取れているが、A-bの外観マッチングは物体の内側の対応が取れていない、という点は共有された [7:44〜8:09]。
- 運んだマスクの図（青の濃さ）: 何を描いているのかが伝わらず、説明に5分以上かかった。最終的に、「t−1で物体の中にあるマスについて、対応先（tの位置）ごとに個数を数え、正規化したもの」と解釈を合わせた。被覆率と呼べるものではない [11:59〜15:48]。
- その上で、先生はおかしな箇所を指摘した [16:40〜20:33]。
  - 明らかに対応先になるはずの場所（右足のあたりなど）が数えられていない。
  - RAFTの図で、t−1の始点がtのマスクの表示範囲から漏れている、または長さ0の移動を全部数えている可能性がある。
  - 「この可視化の仕方はおかしい気がする」という指摘で、ユーザーが見直すことになった。
- A-bの外観マッチングについては、物体の中で入れ替わりはあっても物体の外には出ない、という解釈は妥当（背景と特徴が違うので分離される）とされた。ただし背景を入れていない簡易確認にとどまる [20:33〜20:51]。
- ユーザーの「A-bも補正すれば行けそう、A-aもどちらでも行けそう」という見立てには、先生は納得していない [16:05〜16:40]。

### stateの持ち方：シリアル（ラスタースキャン）か並列（マスごと）か

- 前回の「メモリの制約」の話の意図を先生が補足した [21:45〜23:48]。
  - 64×64＝4,096マスそれぞれに768次元のベクトルがある。全部を1つの状態ベクトル（4,096×768次元）として扱うとメモリに載らない、という話だった。
  - だから、マスを並列に走らせるのではなく、4,096マスをシリアルに（1マスを1時刻として）読むVision Mamba型が、今は主流。
  - 今のV3（マスごとに独立にstateを持つ並列）は、先行研究を調べないうちに手を付け始めた形。どちらが良いかはデザインチョイスとして考える。
- 何に使いたいか: デコーダーに入れて、画像全体の表現に時系列情報を組み込みたい（ユーザー）。物体ごとのstateは手法1やSAMURAI系の先行研究がすでに多い [24:39〜25:32]。
- 先生の整理 [26:42〜28:27]
  - Mambaを入れる場所は何か所もある。場所ごとにどちらが良いかを検討すればよい。
  - 例: デコーダーの最初（画面全体）はラスタースキャン、物体が決まった後は物体領域だけをラスタースキャン、または並列。分けてよい。
  - シリアルか並列かは、情報をどう持たせたいかの違い。CNNのように上下左右の局所的な情報を集めたいのか、ラスタースキャンで画面全体の情報を1つに集めたいのかで設計が違う。
  - スキャンの順番を工夫する案もある。
  - 当日メモ: SAM2に入れる場所によって2種類を使い分ける。空間を1系列にする方でも、スキャン方向を変えるのはあり。
- ユーザーの見立て: 位置合わせ（下記）をするなら並列の方が向く。シリアルにすると位置の情報がなくなる [28:27]。

## 手法2の位置づけ：state をどの単位で持ち、どう対応を取るか

- 前回の質問「なぜ64×64のマスを1マスずつMambaに入れるのか」への答えの訂正：**メモリの制約は理由にならなかった**
    - 全マスを1本の系列にしても、Mambaの計算は系列の長さに比例するので、1フレームあたりの計算はほぼ同じ
    - 持ち越すstate（64×64の段、1物体）は、
        - マスごとだと 4,096マス（64×64）× 1マスあたり10,240 ＝ 約4,200万個
        - 1本の系列なら10,240個
            - むしろ1本の方が小さい
            - 1マスあたり10,240 ＝ Mambaの内部のチャネル512（入力256ch × 2）×（ssm_stateの16 ＋ 畳み込みの窓の4）
    - マスごとにしているのは「位置ごとに記憶を持たせる」という設計の選択

!00-per-cell-vs-one-sequence.png

- 左が今のV3（64×64のマスそれぞれにstateがあり、同じマスへ持ち越す。A-bはこれを対応に沿って運ぶ）。右は、今は試していない形で、全マスを決めた順に読み、1つのstateで次のフレームへ渡す。図は4×4に簡略化
- これまでの空間方向の案を、2つの軸で並べ直した（前回の4パターンは2つの軸が混ざっていた）

| 対応の取り方 ＼ stateの単位 | マスごと | 物体ごと | 画像全体で1本 |
| --- | --- | --- | --- |
| 取らない | 今のV3 |  | 全マスを1本の系列にする（試していない） |
| 近くと混ぜる | B・B'（効かなかった） |  |  |
| 潜在特徴の類似度で運ぶ | **A-b** |  |  |
| 画像のoptical flowで運ぶ | A-a |  |  |
| 物体の動き（boxなど） |  | 手法1（動き予測のMamba）、SAMURAI |  |
- 手法2は「マスごと」で考える
    - 物体ごとのstateは、手法1と役割が重なる
    - マスごとなら、物体の形や部分ごとの情報（変形、部分的な遮蔽）を持てる、と見ている（未確認）
- 近い研究との違い（英論文紹介の2本）

|  | Memory as Dynamics（ICML'26） | TV3S（CVPR'25） | 手法2 |
| --- | --- | --- | --- |
| Mambaのstate | 持ち越さない（直近8フレームの窓で毎時刻作り直す） | 位置（20*20マス）ごとに、動画を通して持ち越す | 位置（1マス）ごとに、動画を通して持ち越す |
| 使い方 | 信頼度が低いときだけ、予測をdecoderに足す | 毎フレーム | 毎フレーム |
| 空間方向 | ― | 隣の位置とshiftで混ぜる | 対応に沿って運ぶ |
| タスク | 追跡（SAM2を固定） | 動画のセマンティックセグメンテーション | 追跡（SAM2を固定） |
- 位置ごとにstateを持ち越すのはTV3Sと同じ。違いは「混ぜる」ではなく「対応に沿って運ぶ」こと。混ぜる方式（②・②'）が効かなかったので、運ぶ方向を主軸にする
- **→ 相談：手法2は「マスごとのstateを、対応に沿って運ぶ」（A-b）に絞ってよいか**

## A-bの改善の候補：対応の取り方を差し替えて比べる

- 前回の「対応付けを差し替えられる形にして、計算量と精度の関係を見る」に沿って、3段で考えている
- 違うのは「tのマスpが、t−1のどこからstateを持ってくるか」を決める部分だけで、運び方とMambaは共通
- 目標：同じ物体から持ってくる性質（運んだマスクのIoU）を保ったまま、物体の内側の並びを揃える
- 図の窓は7×7に簡略化（実際は15×15）。重みは説明用の例

#### **1. 類似度最大（今のA-b）**

!01a-similarity.png

- pと窓の各マスを1マスずつ比べ、似ている度合いで重みを付ける
- 各マスがばらばらに決めるので、隣どうしの移動がそろわない

#### **2. 制約を入れる案**

!01b-constraint.png

- 上下左右の隣が選んだ移動と、1マス以内でそろう候補の点数を上げて選び直す
    - これを数回くり返す
    - 物体の境界ではそろえない
- 前回の「上下左右に制約をかける」古典的な方法（MRF）
    - 「1マス以内」はRAFTでは隣と1マス以上ずれる所が4%しかないことから決める
- 学習なし
    - 追加の計算は類似度の計算の約1/20（見積もり）

#### **3. 周りごと照合する案（本命）**

!01c-surroundings.png

- pの周り3×3と候補の周り3×3の類似度を、小さなネットワークで読んで点数を付け直す（図は対応する9組、実際は全組の81組）
- 点追跡の手法（LocoTrack 2024、CoTracker3 2025）の考え方
    - 似たマスが多い所でも，周りの並びまで比べれば位置が決まる
- 学習するのは対応付けの部分だけ
    - 学習前は今のA-bと同じになる（付け直しの重みを0から始める）
- 追加の計算は約6倍（候補を上位16に絞れば約0.4倍、見積もり）
    - 今の類似度の表から計算できる

**進め方と気になること**

- まず学習なしで、今回の指標（隣とのずれ・折り返し・運んだマスクのIoU）で3つを比べ、良いものだけを学習する
- 気になること
    - 11/6の評価で、推論のときだけ対応をでたらめに並べ替えても、性能の差は小さかった（+0.27 pp、区間は0を含む）。並びを直しても性能が上がるかは分からない
    - 確かめるなら、学習済みのA-bで推論のときだけ対応をRAFTから作ったものに差し替え、性能とstateの寄与が上がるかを見る（対応が良くなったときの上限）
    - 上のウサギの1マスでは、周りごと照合のいちばん簡単な形（学習なしで、周り3×3の類似度を平均するだけ）でも、RAFTの移動先に重みが移らなかった（1マスの例）
- **→ 相談：周りごと照合する案を本命として詰めてよいか。それとも先に、対応が良くなれば性能が上がるか（RAFTに差し替えた上限）を確かめるべきか**
